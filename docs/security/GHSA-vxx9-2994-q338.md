# GHSA-vxx9-2994-q338 / CVE-2026-32314 — yamux oversized `Data|SYN` panic

**Package:** `yamux` (Rust)
**Severity as published:** high — CWE-248 (uncaught exception), CWE-617 (reachable assertion)
**Advisory range as published:** `<0.13.10`
**Resolution:** **not affected.** No yamux version resolved by this repository falls inside the
window that actually carries the defect.
**Date:** 2026-09-25
**Machine-readable record:** [`security/advisory-scope.toml`](../../security/advisory-scope.toml)
**Gate:** `scripts/check-advisory-scope.py` (wired into the fast gate set)

---

## 1. What the advisory claims

> The Rust implementation of Yamux can panic when processing a crafted inbound Data frame that sets
> SYN and uses a body length greater than `DEFAULT_CREDIT` (e.g. 262145). On the first packet of a new
> inbound stream, stream state is created and a receiver is queued before oversized-body validation
> completes. When validation fails, the temporary stream is dropped and cleanup may call
> `remove(...).expect("stream not found")`, triggering a panic in the connection state machine.

Remotely reachable over a normal Yamux session, no authentication required: an attacker who can
establish a session sends one `Data|SYN` frame with `Length = DEFAULT_CREDIT + 1` and the node
panics. The advisory names `0.13.10` as the first patched release, so its published range
(`<0.13.10`) also matches every `0.12.x` release.

## 2. What the code actually does

The defect is a **guard-ordering** bug, not a missing check. The oversized-body guard exists in every
release; the question is where it sits relative to `make_new_inbound_stream`. Reading the region
around the `Data|SYN` arm of `on_data` at each upstream tag
(`github.com/libp2p/rust-yamux`, file `yamux/src/connection.rs`):

| Tag | Guard line | `make_new_inbound_stream` line | Order | Vulnerable |
| --- | --- | --- | --- | --- |
| `yamux-v0.12.0` | 703 | 717 | guard **first** | no |
| `yamux-v0.12.1` | 627 | 643 | guard **first** | no |
| `yamux-v0.13.8` | 620 | 634 | guard **first** | no |
| `yamux-v0.13.9` | 632/634 | 626 | stream **first** | **yes** |
| `yamux-v0.13.10` | 627 | 643 | guard **first** | no |

The regression enters at `0.13.9`. Its changelog entry is *"Improve flow-control credit verification
for window updates (PR 221)"* — that refactor replaced the `shared.window` decrement with
`shared.consume_receive_window(...)` and in doing so moved the length check to **after** the stream
was created, which is exactly the ordering the advisory describes. The fix commit for the advisory,
[`ac71745`](https://github.com/libp2p/rust-yamux/commit/ac71745226b99191249bbbb0420aceba052c150c),
moves the check back above `make_new_inbound_stream`.

So the real vulnerable window is **`>=0.13.9, <0.13.10`** — one release wide. The published
range `<0.13.10` is coarser than that: it also matches `0.12.x`, which never had the bad ordering.

## 3. What this repository resolves

Measured with `cargo tree -i yamux@<version> --workspace` against the committed `Cargo.lock`:

* `yamux 0.12.1` — via `libp2p-yamux` 0.45.2 / 0.46.0 → `libp2p` 0.53.2 / 0.54.1 → `sc-network`.
* `yamux 0.13.10` — the same two `libp2p-yamux` releases.

`libp2p-yamux` depends on **both** lines unconditionally, through the renames
`[dependencies.yamux012]` and `[dependencies.yamux013]`, and its non-test code holds
`Either<yamux012::Connection<C>, yamux013::Connection<C>>` — so both are compiled into the node.
Neither is inside the vulnerable window.

Every lockfile in the tree that names `yamux`, and what it resolves:

| Lockfile | yamux | Note |
| --- | --- | --- |
| `Cargo.lock` | `0.12.1`, `0.13.10` | the workspace that ships |
| `crates/x3-sidecar/Cargo.lock` | `0.12.1`, `0.13.10` | nested workspace |
| `patches/sc-rpc-server/Cargo.lock` | `0.12.1`, `0.13.8` | a vendored crate's own stale lock; cargo ignores the lock of a path dependency |

`0.13.8` is on the safe side of the window as well (table in section 2), so **no lockfile in the
tree resolves a vulnerable `yamux`**, and none contains `0.13.9`.

That the `0.12.1` copy is compiled is the reason this advisory was worth taking seriously: the crate
*is* in the node's live code path, so the only question was the ordering, and the ordering is correct.

## 4. Why nothing in the repository flagged this, and why it still will not

* **RustSec has no advisory for yamux at all.** The repository's dependency gate is
  `cargo-audit`/`cargo-deny` against the RustSec database; GitHub's Dependabot uses the GitHub
  Advisory Database. `GHSA-vxx9-2994-q338` carries identifiers `GHSA` and `CVE` only — no `RUSTSEC-`
  id — so the repository's own gate cannot see it and never said anything.
* **Dependabot will keep reporting it.** Its comparison is against the published range `<0.13.10`,
  and `0.12.1` matches that range. There is no lockfile change that clears the alert, because the
  resolvable versions are already outside the real window. Suppressing it in `cargo-deny` is not
  possible either (there is no RustSec id to suppress), and suppressing it silently would be the
  wrong answer for a *reachable* crate.

That is the gap `security/advisory-scope.toml` + `scripts/check-advisory-scope.py` close. The check
does not take the judgement on trust: it re-reads every `Cargo.lock` in the tree on every run and
fails if a resolved version of `yamux` ever lands inside `>=0.13.9,<0.13.10`, or if the resolved set
drifts from the recorded `["0.12.1", "0.13.8", "0.13.10"]` — which is what a well-meaning lockfile bump would
do, turning a recorded judgement into a stale claim. A bump that pulled in `0.13.9` fails it; a bump
that dropped `0.12.1` also fails it, and forces this document to be re-verified.

## 5. How to re-verify

```bash
# The record and the gate.
python3 scripts/check-advisory-scope.py --list
python3 scripts/check-advisory-scope.py

# What the lock actually resolves.
cargo tree -i yamux@0.12.1 --workspace
cargo tree -i yamux@0.13.10 --workspace
grep -n 'name = "yamux"' -A1 Cargo.lock

# The ordering at each upstream tag (the table in section 2).
for tag in yamux-v0.12.1 yamux-v0.13.8 yamux-v0.13.9 yamux-v0.13.10; do
  gh api "repos/libp2p/rust-yamux/contents/yamux/src/connection.rs?ref=$tag" --jq .content \
    | base64 -d \
    | grep -n 'make_new_inbound_stream(stream_id, DEFAULT_CREDIT)\|exceeds default credit'
done
```

If a future SDK/libp2p bump resolves `yamux 0.13.9`, or drops the `0.12` line entirely, the gate
fails and this document is the place to start.
