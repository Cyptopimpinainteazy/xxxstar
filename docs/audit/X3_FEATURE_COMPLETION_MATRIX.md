## How the state column is derived

The state is a pure function of the row's own recorded scores. The first rule that
matches wins, so a reader can re-derive every cell from the JSON artifact.

| State | Rule |
|---|---|
| BROKEN | a cited path does not exist on disk, so the row cannot be built from |
| NOT INTEGRATED | source is not master (open PR or research), so it is not in the tree under test |
| COMPLETE | implemented >= 80 and tested >= 80 and mainnet_ready >= 80 |
| FUNCTIONAL BUT UNHARDENED | mainnet_ready >= 60 |
| PARTIAL | implemented >= 50 |
| STUB | implemented >= 20 |
| NOT STARTED | implemented < 20 |

A state is **not** a launch approval. `COMPLETE` means the three recorded scores are
at or above 80; whether those scores themselves are honest is what the registry's
`required_tests`, `proof_report` and blocker text are for.

### state_snapshot — 70% (GUARDED_TESTNET)
- The exporter consumes `export-state` output rather than reading the database directly, so the operator flow is export-state -> build -> verify -> restore, and nothing yet reads the trie straight out of the database.
- Restore produces a raw chain spec whose genesis state is block N's state, but nothing installs that state behind block N's header. A node booted from it recomputes the same state root and then refuses to author (`frame-system`: 'Block number must be strictly increasing') because its header is number 0. Joining a running chain at a height is state/warp sync and is a client-level path that does not exist here.
- The largest state this has been exercised against is one dev chain: 12,526 entries (block 6290) and the repository's own 6 MB raw spec fixture (12 chunks at 256 KiB). Chunk counts, chunk sizes and export wall-clock at production state sizes are unmeasured, and `export-state` on a node with bounded state pruning fails with `UnknownBlock("State already discarded")` for any block whose state has been pruned — a snapshot source has to archive state or export at the head.
