## The defect

`require slippage <= 1%` did not parse. Measured from the known-good
`examples/timeout_refund_minimal.x3` with one guard inserted before its `timeout`:

```
require slippage <= 50      OK
require slippage <= 0.5%    OK
require slippage <= 1%      FAIL  unexpected clause in intent body: Ident("45s")
require slippage <= 2%      FAIL  unexpected clause in intent body: Ident("45s")
require delta <= 0.01%      OK    (parses; then a semantic error, unrelated)
```

The literal reader's own comment says why the split is whole-versus-fractional: "`70%`
is an integer followed by `%`, while `0.5%` is a single percentage literal whose text
still carries the sign". Only the dotted form was implemented, so `1%` kept its `%`, the
expression parser took it for the **modulo** operator, and it consumed the next token as
its right-hand operand — in a guard, the next clause. The refusal named `45s`, a line
that was correct.

It survived because a percent guard written *last* in a body has no following clause to
swallow, which is where every passing example and fixture happens to put its own.

## Where the fix went, and why not where the comment pointed

The first attempt implemented `Int.Percent` in the literal reader — exactly what that
comment promises. It broke a test:

```
compiler/tests/test_parser_coverage.rs::expression_arithmetic
  fn f() { let x = 1 + 2 * 3 - 4 / 5 % 6; }
```

`5 % 6` is a modulo between two integer literals and a real expression. Claiming every
`Int` followed by `%` as a percentage takes something away, so the fix moved to the
guard's bound — `parse_guard_bound`, a two-token lookahead — which is where the language
documents the percent spelling. The literal reader's comment now says which form it
implements **and that the omission is deliberate**, rather than promising something the
code does not do.

That is the round's own lesson applied to itself: a comment promising `Int.Percent` sent
me to the wrong fix site, and the test that caught it was one I had not read.

## The boundary, pinned rather than discovered

`a_percent_in_a_guard_bound_is_a_percentage_and_a_modulo_everywhere_else` asserts three
things, so the narrowing is on the record:

1. `totals % slots` — a modulo between non-literals, untouched.
2. `let x = 1 + 2 * 3 - 4 / 5 % 6;` — a modulo between integer literals outside a guard,
   untouched. This is the case that decided the fix site.
3. `require … == 1%` — a percentage, the point of the fix. So a modulo between literals
   *inside a guard's bound* needs parentheses (`(5 % 6)`, also asserted).

Point 3 is a deliberate narrowing. The spelling it replaces produced a guard whose value
was the text `5 Percent 6` — a bound nobody wrote — so nothing that meant anything was
taken away. **TICKET-089's acceptance criteria said the fix must not remove `%` from the
operator table**, and it did not: the table is unchanged, and only a guard's bound claims
the adjacency. The criteria did not anticipate that `Int %` *inside a bound* would have to
be claimed, and that refinement is recorded here rather than in the ticket's silence.

## A test in the tree was passing for the wrong reason

`test_slippage_units.rs::the_mainnet_ceiling_reads_the_same_unit_as_the_guards` asserted:

```rust
("require slippage <= 5%", "500", /* accepted */ false)
```

It "passed" only because the guard failed to **parse** — `compile_with_mode` returned
`Err`, and the assertion on `is_ok()` was satisfied by a syntax error rather than by the
ceiling comparison the test names. With the parse fixed, `5%` is 500 basis points against
a 500 basis point ceiling and the check refuses only what is *above* it
(`semantic.rs`: `bound > policy`), so the honest expectation is `true`.

A second row was wrong in the same direction and for an unrelated reason: `("require
slippage <= 501", "501", false)` is a bound equal to its ceiling, which is inside. The
table is now five rows that each test the boundary it describes — equal is inside, above
is refused — with two percent rows so `5%` and `0.5%` are pinned as 500 and 50 basis
points. Nothing about the compiler changed to make them pass; the expectations were
recalibrated against the semantics the code actually has.

This is the fourth instance this session of the same pattern, and it is worth naming
plainly: **a test whose input cannot express the property it asserts.** Before it was
`verify_valid_receipt` succeeding against `block_hash = [0xab; 32]`, a `keccak256` test
asserting "not all zeros", and a determinism property generating a one-entry map. Here it
is an assertion about a ceiling that was satisfied by a parse error.
