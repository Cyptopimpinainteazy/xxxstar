## 1. The types, and the audit answered by test

`crates/x3-common/src/fixed.rs` (482 lines) holds `Bps`, `Decimal<const
SCALE: u8>`, `Ratio`, `Rate`, `Price`, `RoundingMode`, `pow10`, `MAX_SCALE`.

The design decisions that make the audit items into *properties* rather than
comments:

- every operation is `checked_*` and returns `None` — nothing wraps;
- the mantissa is **unsigned**, so underflow cannot produce a negative amount:
  subtracting more than there is returns `None`;
- every lossy operation takes a `RoundingMode`, and `Exact` **refuses** a loss
  rather than stating one;
- a zero divisor returns `None`; there is no infinity and no NaN to propagate;
- `pow10(19)` is `None`, so a scale the type cannot hold is refused rather than
  truncated;
- `Rate` carries its interval in blocks and `Price` carries its pair, so a rate
  that does not say over what and a price used against the wrong pair are
  refusals rather than silently-wrong numbers.

`RoundingMode` moved from `crates/x3-ast/src/trading.rs` into `fixed.rs`; the AST
now re-exports it, so the direction a declaration writes and the direction an
amount conversion obeys are one type rather than two that happen to agree.

**Evidence — twelve tests, one per audit item plus the vocabulary itself**
(`crates/x3-common/tests/fixed_math.rs`), and one cross-crate identity test
(`crates/x3-ast/tests/trading_ast.rs`):


## 2. Writing the tests found two real defects in the module

This is the part worth keeping. Both were in the *new* code, and both were found
by the audit tests rather than by review.

**`Ratio::of` overflowed for every amount the language writes.** It scaled both
sides to 18 digits and then divided — multiplying two 18-digit mantissas:

```
before  Ratio::of(1_000, 999)      -> None        (9.99e20 × 1e18 > u128::MAX)
after   Ratio::of(1_000, 999)      -> 0.999       (one scaling: 999 × 1e18 / 1000)
```

The same double scaling was in `Ratio::of_amount` and `Rate::over`; both are now
the integer form (`mantissa × amount / 10^18`, `ratio × blocks / per_blocks`), so
the intermediate cannot overflow on an ordinary quantity.

**`Price::convert` refused any amount above roughly 227 units.** Same
double-scaled product. It now cancels the powers of ten the two sides share —
the ratio's trailing zeros, then any the amount has — before forming the
product. Cancelling is exact, so there is still a single rounding and it is the
one the caller asked for:

```
2 ETH       @ 18 dec, quote 6 dec, ratio 1.5 -> 3_000_000        (Exact)
1_000_000 ETH                                 -> 1_500_000_000_000 (Exact)
1 wei ETH                                     -> None / 0 / 1     (Exact / Down / Up)
```

The last row is the point of the pair-in-the-value design: one wei of the base
asset is worth less than one base unit of the quote asset, so the direction is
the caller's to state rather than the conversion's to guess.

## 3. The types are adopted, not decorative

A type nothing calls is not an implementation. Two kinds of adoption landed:

**The unit is named.** The bare `10_000` that was the basis-point ceiling was
spelled in seven files. It is now `Bps::WHOLE` / `Bps::is_within_whole()`:

| file | before | after |
|---|---|---|
| `arb.rs` | `margin >= 10_000` | `margin.raw() >= Bps::WHOLE.raw()` |
| `semantic.rs` | `venue.fee_bps >= 10_000`, `slippage_bps > 10_000` | `>= Bps::WHOLE.raw()`, `!is_within_whole()` |
| `trading_semantic.rs` | `max_slippage_bps > 10_000`, `max_flash_fee_bps > 10_000` | `!is_within_whole()` |
| `trading_verify.rs` | `max_slippage`, `max_oracle_deviation`, `max_flash_fee > 10_000` | `!is_within_whole()` |
| `verify.rs` | `royalty_bps > 10_000`, `total != 10_000`, three policy ceilings | `!is_within_whole()`, `!= Bps::WHOLE.raw()` |
| `objective.rs` | `value > 10_000` | `!is_within_whole()` |
| `strategy.rs` | `const MAX_BPS: u32 = 10_000;` | `= Bps::WHOLE.raw();` |

Every diagnostic string is byte-identical, because several tests assert those
figures (`test_arb.rs` matches on `"the whole trade"`).

**The arithmetic is typed.** `HedgeExposure::delta_bps` — the one security-
relevant computation PHASE 9 rests on — is now `Ratio::of(long, |long − short|)`
then `Ratio::to_bps(Down)` instead of a bare `× 10_000 /`. The truncation point
is the same (for positive integers `floor(floor(x)/n) == floor(x/n)`), so the two
existing `hedge.rs` tests are unchanged, including the 1_000 bps figure a 900-against-1_000
hedge produces.

Where the notional is too large for the fixed-point conversion the delta is
reported as `u128::MAX` rather than as a small plausible number. Every declared
bound is below that, so the hedge is **refused rather than admitted** — the
fail-closed direction. This is a behaviour change at that extreme and it is
deliberate rather than silent: `hedge.rs` documents it at the call site.
