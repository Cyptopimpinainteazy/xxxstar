## Why the question came first

Round 58 left PHASE 48's last six cases as a named gap, and the gap was not a
test-writing gap: a test has to assert a documented behaviour, and there was no
documented behaviour to assert. `restart during execution`, `process kill`, `partial
domain outage`, `RPC outage`, `reorg simulation` and `ledger corruption` are all the
same question — *which state outlives a process?* — so the decision came first and the
tests assert it.

## The decision

**Nothing survives a run.** `.ai/reports/x3lang-ticket087-decision-20260919.md` records
it per candidate:

| state | why it is not persisted |
|---|---|
| the open atomic plan | it is a region of the artifact; re-executing reaches the same state, because emission is deterministic (PHASE 42) |
| the trading journal | derived from execution; a disk copy would be a second source of truth for figures `TradingVm::profit` already reconciles |
| the receipt | already the durable form — PHASE 45's version binding and TICKET-017's legs make it re-derivable rather than necessary to persist |
| the finality view | a cached view is a stale view; the `reorg simulation` test exists because the verdict must follow the view the caller holds *now* |

**And the consequence stated rather than assumed: an interrupted atomic plan is not
resumed — it is not executed at all.** That is the fail-closed reading, and it is a
legitimate answer rather than a placeholder: a plan that did not commit has no receipt,
and a plan with no receipt has nothing a settlement layer can act on. The alternative,
persisting a half-executed plan and resuming it, would add a trusted on-disk surface for
every intermediate state — each needing its own version binding, torn-write rule and
corruption check — bought for a capability the artifact and receipt pair already
provide by re-derivation.

## The defect the question found

Answering it found **one** piece of state that did outlive a run, and it was not the
plan.

`ProductionBridgeAdapter::storage_op` and `lifecycle` reached two
`static Mutex<HashMap<…>>` behind accessor functions, so the host storage a program's
`storage_store`/`storage_load` uses belonged to the **process**:

```
before  two adapters in one process shared it; COUNT grew across runs
        test FAILED: "a fresh adapter read another run's storage — the storage belongs
        to the process, not the run"
after   the storage and the lifecycle states are fields on the adapter
        test ok
```

Both runs were performed, by temporarily restoring the global — this is the
before/after, not a description of one.

The path is reachable from the language: `storage_store`/`storage_load` lower to
`Operation::StorageOp` (`lowering.rs:1386`, `1634`) → `CapabilityPayload::StorageOp`
(`emitter.rs:871`) → `bridge.storage_op` (`executor.rs:1150`). So the same artifact over
the same inputs answered differently depending on what had run before it — a determinism
defect as much as a durability one, and the same class as round 57's artifact
non-determinism.

A caller that *wants* the storage to persist across runs now says so by reusing one
adapter: a decision at the call site rather than a property of the process. The maps are
`BTreeMap` for round 57's reason — a map nothing orders today is a trap for the first
reader that lists it.

## The six cases

| case | test | what it asserts |
|---|---|---|
| restart during execution | `restarts_and_kills_leave_nothing_behind` | a fresh VM is the empty journal; two fresh VMs over the same ops reach the same state |
| process kill | `restarts_and_kills_leave_nothing_behind` + `a_receipt_exists_only_for_a_committed_plan` | nothing is left behind, and the one record that leaves a run is complete or absent — never half-written |
| partial domain outage | `an_unreachable_second_domain_rolls_the_plan_back` | the host refuses the bridge; the manifest **lists** it, so the refusal is the domain and not the capability; the half that ran is rolled back |
| RPC outage | `a_host_that_stops_answering_mid_plan_rolls_the_plan_back` | the host goes quiet on the **second** swap, after the first leg committed; silence is not a zero and not a success |
| reorg simulation | `a_reorged_finality_view_refuses_a_proof_that_was_final` | a header that was trusted is refused once the view moves, and trusted again when the reorg is undone — so the verdict follows the view rather than a cached first answer |
| ledger corruption | six tests in `vm/tests/trading_receipts.rs` | see the correction below |

`restart` and `process kill` share one test. That is honest rather than a shortcut: the
difference between them is whether the process comes back, and the claim being tested is
that it does not matter, because nothing was left behind either way.

## A correction round 58 owed

Round 58 counted `ledger corruption` as uncovered on 2 keyword hits. **That was wrong.**
`vm/tests/trading_receipts.rs` covers it with six tests:

```

failed_receipt_cannot_report_profit

```

The matrix file's own method section said "a count is a pointer, not proof". The pointer
was wrong, and doing the work is what showed it. Three things came out of that:

- the matrix now carries **test names** for that row instead of a count;
- PHASE 48 is **29 of 30** rather than 23, with `dropped transaction` the only
  unverified row — and it is stated as *unverified* rather than quietly counted as
  covered, because that is exactly the mistake this file already made once;
- the lesson generalises: a keyword count is a way to *find* candidates, not a way to
  decide coverage. Every row in the matrix that is now marked covered is marked because
  a test was read.

## A cross-agent note worth carrying

`master` moved mid-round to `afa6b562c` — PR #361, "the embedded runtime could not link
std — the intent crate took the verifier's default features". That is **a consequence of
my TICKET-065 change**: adding `x3-verification-router` as a plain path dependency
pulled its default `std` feature into `pallet-x3-settlement-engine`'s wasm graph.
Another agent found it and fixed it with `default-features = false` plus
`std = […, "x3-verification-router/std"]`.

The lesson is worth writing down because it is not obvious from the diff that did it:
**adding a path dependency is a feature-unification decision.** In a workspace where one
member is built for `wasm32v1-none`, `{ path = "…" }` is not a local decision — it
carries that crate's default features into every graph it joins.
