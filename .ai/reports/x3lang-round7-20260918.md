# X3Lang round 7 — `x3c explain` printed garbage for any program with a nonce

Merged to `origin/master` as `8446839f4`. 1 file, +75/-4.

## The defect

`disassemble` (behind `x3c explain`) walked the compiler header with
`align4(pc + 3 + len)` for the nonce and `pc += 5` for `chain_id`, while
`emit_x3ir` writes both unpadded and writes `chain_id` as a `u64`. Two
independent mismatches, either of which desynchronises the walk:

```
$ x3c explain <bytecode for examples/simple_swap.x3>      # before
  0000  meta.nonce   = "simple_swap_001"
  0001  0x1b  OP(0x1b)
  0002  0x73  VECTOR   rce_lock_proof intent ...
```

`rce_lock_proof` is `source_lock_proof` with three bytes eaten, and the walk
never recovered: `LOCK`, `BRIDGE` and `RELEASE` were unreadable, so
`b52_test::parse_roundtrip_ir_bytecode` was asserting on a trace that no longer
contained `BRIDGE`.

## The fix

The reader now mirrors the writer exactly — no alignment, `u64` chain id:

```
$ x3c explain <bytecode for examples/simple_swap.x3>      # after
  0000  meta.nonce   = "simple_swap_001"
  0001  0x83  CAP      IntentResolve { constraints: [], resolver: "simple_swap" }
  0002  0x20  LOCK     Lock { chain: "arbitrum", asset: "USDC", amount: 500, from: "sender" }
  0003  0x23  RELEASE  Release { chain: "solana", asset: "SOL", to: "wallet" }
  0004  0x50  ATOMIC_BEGIN
  0005  0x25  BRIDGE   BridgePayload { via: "X3", ... }
  0006  0x51  ATOMIC_END
```

The flagship `examples/mainnet_safe_swap.x3` decodes 28 instructions.

## What was deliberately not changed

The writer *also* disagrees with the VM: `pad_to_4`'s doc says "the X3 VM
verifier requires every instruction to start on a 4-byte boundary" and the VM's
`first_instruction_pc` aligns the metadata block, but `emit_x3ir` does not pad
it. A 15-byte nonce therefore leaves the first instruction at offset 19.

I tried padding the writer. It makes the disassembler agree, and it **breaks
`evm_call_pipeline` and `x3_call_pipeline`**, which pass with the current
layout. The writer, the VM reader and the alignment invariant have to be settled
in one change with the bytecode fixtures updated alongside; shipping half of
that trades one reader for another. TICKET-023 has the full evidence.

Related, also filed: when `proofs required` is the *first* item, `x3c run` fails
with `InvalidOpcode`, while the same ops mid-stream in
`examples/mainnet_safe_swap.x3` execute fine (that program only fails later on a
real business rule, `solver bid: fee must be non-empty`). Something about the
first instruction after the header is still uncharacterised, and I would rather
name that than guess.

## Also held back

The proof requirement is over-broad: it triggers on `Lock`, and intent lowering
emits the `from` endpoint as a `Lock`, so a same-chain intent is told it needs a
source-lock proof for a transfer that never crosses a chain (measured on
`internal_transfer`: one warning, nothing locked). Gating it on `has_bridge` is
the right fix and was written and verified, but promoting it to an error widened
`PROOF_REQUIRED` exposure across six corpus programs and ran straight into the
header problem above. Held rather than shipped on an unsettled format —
TICKET-024.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 534 passed, 0 failed   (532 before)
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0

x3c explain <nonce-bearing program>   -> correct instruction stream (was garbage)
x3c explain examples/mainnet_safe_swap.x3 x3b      -> 28 instructions decoded
```

Two tests added: a 15-byte nonce must not shift the stream (the offset that made
the bug visible), and `chain_id` must be read at its real width.

## Round note

This round's honest shape is: one real fix merged, two findings characterised and
filed rather than half-fixed. The pattern across this session — a check that
exists but is not on the path that matters, or a reader and writer that drift
apart — showed up again here in the header format, and the same discipline
applies: do not change one side of a format by itself.
