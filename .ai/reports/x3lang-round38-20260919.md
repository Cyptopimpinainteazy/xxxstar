# X3Lang round 38 — 2026-09-19 — `route_score` gains a declaration (TICKET-049/050)

Landed on `master` as `bd9e8f67b` (base `d7585537d`; another agent's workspace
burn-down landed mid-round and this branch rebased onto it, then re-ran the suite).

## The hole

Six corpus programs required `route_score >= 85..90` and **nothing anywhere
declared a route score**: no declaration to compare against, no run-time quantity,
and a `REQUIRE` the executor treats as true. Of every unbacked guard kind this was
the most-used in the corpus.

`risk_policy` gains `min_route_score <n>` — where a program states the score it
accepts — and the guard is checked against it in the shape `solver_bond` and
`relayer_quorum` already use:

- a floor (`>=`) is required, because a ceiling would say the route may not score
  *well* and comparing that against a declared minimum answers a question nobody
  asked;
- a guard with no declaration is refused, naming the clause to add;
- a guard demanding more than the declaration is refused with both figures.

## TICKET-050, in the same clause

`parse_risk_policy_item` ended with `_ => { self.advance(); }` — "skip unknown
config fields" — while its own doc comment advertised `max_fee`, `max_route_risk`
and `min_liquidity`, none of which it read. A program writing one of them declared
a bound that was dropped without a word: the same defect as a timeout unit that is
ignored. An unknown field is now refused by name alongside the fields that exist,
and the doc comment says what the parser reads.

## The examples declare what they require

`simple_swap`, `staking_intent`, `route_fallback` and `multi_leg_route` (which had
no `risk_policy` at all) gain `risk_policy { min_route_score <their own guard> }`;
`flagship_b52` and `mainnet_safe_swap` gain the field inside the block they already
had. A test asserts the corpus invariant — every example containing
`require route_score` also declares a score — so it cannot drift.

## Two things found by doing it

**An invented slippage bound was reverted, and the reason is a defect.**
`multi_leg_route` requires `slippage <= 120`, so the insert first copied that into
the new policy as `max_slippage 120`. That made the program *stop running*:
`risk_policy.max_slippage` is lowered as a `RiskScore` capability whose score the
VM requires to be at most 100, so a 120 bps slippage bound became an invalid risk
score and the corpus's run count went 17 → 16 with
`VM error: Panic("risk score: score must be <= 100")`. The examples now declare
only the score they require, and the unit conflation is TICKET-052.

**Two test fixtures carried the same unbacked guard.**
`crates/x3-tools/tests/cli.rs`'s fully-configured source and a
`test_canonical_supply.rs` probe (which used `require route_score >= 1` as filler)
both had to be fixed rather than having the new check loosened for them — the
fixtures are programs, and a program has to satisfy the language.
