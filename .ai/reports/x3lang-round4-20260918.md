# X3Lang round 4 — warnings are no longer discarded

Merged to `origin/master` as `841cdeb60`, fast-forward from `ae5c1bbe1`
(`origin_only=0 branch_only=1`). 4 files, +347/-58.

## The defect

`verify_with_config` ended with:

```rust
if acc.has_errors() { Err(acc.take_errors()) } else { Ok(()) }
```

`ErrorAccumulator` collects warnings, but nothing ever read them. **Any safety
check written as a warning in this verifier was dead code.** That is the root
cause behind three separate silent holes found earlier in this session:

| Check | What it did | Consequence |
| --- | --- | --- |
| `verify_finality_explicit` | warned | a bridge with no source-finality requirement compiled clean |
| `verify_proof_requirements` | warned | a bridging program with no proof declaration compiled clean |
| `verify_invariants_structured` | warned | six builtin invariant violations were invisible |

## The fix

- `semantic::VerifyOutcome { errors, warnings }` and `semantic::verify_collect`
  run the same pass list and return both. `verify_with_config` is now a thin
  wrapper over it, so every existing pass/fail caller is unchanged.
- `check_source_diagnostics` / `check_source_diagnostics_with_mode` expose the
  outcome; `check_source` / `check_source_with_mode` stay as error-only wrappers
  for API compatibility.
- `x3c check` prints warnings to stderr and adds them to its JSON output.
- New global `--deny-warnings` flag makes warnings a non-zero exit, so "no
  warnings" is enforceable in CI. It is opt-in, so nothing starts failing
  silently.
- The check path's verifier budgets now use `DEFAULT_MAX_ATOMIC_OPS` /
  `DEFAULT_MAX_ROUTE_HOPS` rather than the literals `8` / `4`.

## Measured effect

```
$ x3c check examples/mainnet_safe_swap.x3      # before: "no semantic errors", nothing else
{
  "operations": 28,
  "status": "ok",
  "warnings": [
    "Semantic error: Lock operation present without `proofs required { lock_proof }` declaration",
    ...

$ x3c --deny-warnings check examples/mainnet_safe_swap.x3   # exit 1
$ x3c --deny-warnings check <warning-free Trading Core v1>  # exit 0
```

## What this exposes

`tests/conformance/valid/intents/internal_swap.x3` — a well-formed intent —
now reports **7 warnings**, because the six builtin invariant rules reason about
linear position in an IR whose `from`/`to` endpoints are emitted *before* the
route body. Those rules are false positives against the intent surface.

That is a pre-existing defect (measured and documented in round 2, see
`x3lang-intent-guards-20260918.md` F1) that has now become *visible* instead of
hidden. Fixing it is TICKET-002, and it is now the most valuable next item
because `--deny-warnings` cannot be turned on until it is resolved.
