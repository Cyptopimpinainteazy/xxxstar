# X3Lang round 37 — 2026-09-19 — three more guard kinds get a checker (TICKET-027)

Landed on `master` as `4105ebc48` and `f5605f857` (base `5e89e6c7d`).

## What changed

**`proof_complete` is compared against `proofs required { … }`.** The guard asserts
a proof of a named type was completed, and `proofs required` is where a program
declares which proofs its operations need — so the two are checkable against each
other, the same shape as `solver_market.bond` and `relayers { quorum N_of_M }`.
The message names both sides:

```
declaration 'probe' requires the proof 'solver_signature' to be complete, and the
program declares {source_lock_proof, destination_fill_proof} — a proof it never
declares is one no operation can carry
```

A program with no `proofs required` at all is told that, and a guard naming nothing
is told what to write.

**An unknown guard kind is refused.** `require_kind_from_str` carries a word it does
not know as `Custom`, which is how `require proof verified` parses — and a `Custom`
guard has no declaration to compare against, no run-time quantity and no verifier
reading it: it lowers to a `REQUIRE` the executor treats as always true. The
language's rule everywhere else is that a construct the compiler does not
understand is one it cannot check ("permissions" are a closed set for exactly that
reason), so a guard kind is closed too and the diagnostic lists the kinds that
exist. `examples/arb_solana_eth.x3`'s `require proof verified` is now refused
instead of recorded as true.

**`require refund_path` is decided against the program's own shape.** Whether a
refund path exists is computed in `verify_refund_path_exists` already; the guard is
decided there rather than recorded. The existing check fires only for a program
with a cross-chain operation — the guard can be written anywhere, so the new one
does.

## The count

| | before this round | after |
|---|---|---|
| kinds decided by the compiler | 3 | **5** |
| kinds partially evaluated | 3 | 2 |
| kinds closed by refusal | 0 | 1 (a word the compiler does not know) |
| kinds unbacked | 7 | 5, plus four property kinds named individually |

`vm_supported`, `mainnet_safe`, `audit_gate` and `invariant` are now listed one
row each rather than behind "the property kinds", because each needs its own
decision (a declared value to compare against, or a refusal).

`compiler/tests/test_guard_declarations.rs` — 8 tests. Two of them are there to
keep the change from being broader than it says: one asserts that a **known** kind
with no checker yet (`route_score`, TICKET-049) is still accepted, and one walks
`REQUIRE_KIND_NAMES` asserting every listed name is one the parser accepts —
otherwise the diagnostic would send a user to write a guard that gets refused.

## What this round did not do

`route_score`, `risk`, `bridge_liquidity`, `finality` and `nonce` remain unbacked.
Each needs a declaration (or, for the nonce, a registry) that the language does not
have, and TICKET-049's per-kind acceptance criteria exist so that one is not
invented at a time. `route_score` is the sharpest: six examples require
`route_score >= 85..90` and nothing anywhere declares a route score.
