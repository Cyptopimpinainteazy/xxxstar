# X3Lang round 10 — guards stopped testing unrelated register residue

Merged to `origin/master` as `c1306b929`, rebased onto the then-current master
and fast-forwarded. 3 files, +137/-31.

## The defect

`REQUIRE` tested register `r0` for non-zero, and nothing set `r0` *for the
guard*: it held whatever the previous instruction left there. On the flagship
example the failing guard sat right after three `PROOF_REQUIRED` ops, and the
mechanism is in the executor — the bulk capability arm ends with
`registers[0] = bytes_to_register(&result)` while `ProofRequired` returns an
empty vector, so an unrelated instruction's empty result was enough to fail a
guard. The same residue could as easily pass one that should fail. Both flagship
mainnet examples died there.

## The fix

The instruction frame already had a flags byte and a `u16` operand that
`REQUIRE` ignored. It now carries `[comparison][threshold]`:

```
REQUIRE_COMPARE_STATIC = 0   the guard asserts something about the artifact's
                             configuration; the compiler checked it, and there is
                             nothing for the VM to test
REQUIRE_COMPARE_GE     = 1   r0 >= threshold
```

An unimplemented comparison code fails closed rather than passing by default.
Two supporting fixes: `RelayerAttest` leaves the swarm's quorum numerator in
`r0` — the quantity `require relayer_quorum >= N` is about — instead of the
signature count, which is zero for every compiled artifact; and the bulk
capability arm only moves its result into `r0` when there is one, so a
declaration's value is no longer overwritten by the register encoding of an
empty vector.

## What is deliberately not done

**Nothing emits `REQUIRE_COMPARE_GE`.** I wrote the mapping — `RelayerQuorum` and
`RouteScore` to a comparison, threshold parsed from the guard's condition — and
then measured it: for `require relayer_quorum >= 4` the emitter does write
`flags=01 threshold=4`, but `r0` at that guard does not hold the quorum. The
declarations sit at the top of the program and the guards at the bottom, so the
value there is whatever the last unrelated instruction left. Comparing it would
be a *new* wrong answer rather than a fix, so the emitter emits `STATIC` for
every guard today and says why in a comment. The receiver is implemented and
tested for the point at which the data flow arrives.

That is the honest position: the coin flip is gone, and what replaces it for
most guards is "the compiler checked this", not "the VM checked this" — which is
true for configuration assertions like a declared quorum and false for anything
that has no declaration behind it at all (`require solver_bond >= 10000` has no
bond, in either place). Both halves are TICKET-027.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 540 passed, 0 failed
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0
```

One old test pinned the removed behaviour and was corrected rather than deleted:
`require_fails_when_zero` asserted that `REQUIRE` with `r0=0` panics. It is now
four tests — a static guard must not depend on `r0`, a compared guard fails
below its threshold, passes at it, and an unknown comparison code fails closed —
and `on_fail_catches_require_failure` uses a compared guard so it still
exercises the handler path.

Corpus, end to end through build → verify → execute:

```
before: 7 clean, 2 runtime failures
after:  9 clean, 0 runtime failures

examples/mainnet_safe_swap.x3  ->  ok — 2 asset ops, 1 bridge ops, 3 receipts
examples/flagship_b52.x3       ->  ok — 3 asset ops, 1 bridge ops, 3 receipts
```

Every example that compiles now runs. The remaining seven do not build (the
pseudocode and Python-dialect files, TICKET-013/014).

## A note on one measurement

While confirming the above I counted the emitted instructions two different ways
and got different answers; the hexdump then showed eight `REQUIRE` frames where
`x3c explain` reported four. I have filed that as TICKET-028 *as an observation*
rather than a conclusion, because my first two counts disagreed with each other
and the right next step is to instrument the walk rather than trust a third
hand-rolled count. It does not affect what shipped here — the corpus runs to
completion either way — but it means one reader may be under-reporting.
