# X3Lang round 13 — two of the compiler's three verification layers were dead

Merged to `origin/master` as `1c8c35d59`, fast-forward from `f2b972a3c`.
4 files, +112/-4.

## The finding

`compiler/src/lib.rs` opens by documenting its verification pipeline:

```
1. numeric::verify_numeric_policy — integer literal and coercion policy, over the AST
2. verify::verify_ir             — structural IR invariants before emission
3. semantic                      — whole-program semantic safety
```

Only layer 3 was reachable. A repo-wide grep for the other two returned their
definitions, their own tests, and that doc comment — **no call site in the
pipeline**:

```
$ rg -n '\bverify_ir\b' --glob '*.rs' .
compiler/src/verify.rs:12:pub fn verify_ir(...)
compiler/src/lib.rs:8://! 2. [`verify::verify_ir`] — structural IR invariants ...
compiler/tests/test_ir_verifier.rs: ... (tests only)
```

So the integer-literal and coercion policy, and the structural invariants —
atomic scoping balance, non-zero amounts and iterations, empty-field safety —
were applied to no program that was ever compiled. The crate documented a
pipeline it did not run.

## The wiring

Layer 1 joins `ast_level_errors`, next to the atomic-swap and solver-bond checks.
Layer 2 runs after lowering, on both `compile_with_mode` and
`check_source_diagnostics_with_mode`. Diagnostics are carried as errors with
their stable code visible (`X3E0501: ...`), so tooling can still key on the code.

## What wiring a dead check bought, immediately

Two shipped examples stopped building, and both were genuinely wrong:

```
examples/multi_leg_route.x3   X3E0501: program[4]: swap min_output must be greater than zero
examples/flagship_b52.x3      X3E0501: program[20]: swap min_output must be greater than zero
```

Each contains a swap with no `min_output`, which lowers to an output floor of
zero — a swap that accepts any output at all. That is precisely the
unbounded-slippage case the structural layer exists to catch, and it had been
sitting in two examples the repository uses to demonstrate cross-chain
behaviour. Both now declare a floor.

Nothing else in the corpus or the test suite violates either layer, so the
wiring is additive for correct programs: 548 tests pass and the corpus executes
9 of 16 with 0 runtime failures, exactly as before. The difference is that those
nine now pass three layers instead of one.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 548 passed, 0 failed
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0
corpus build+verify+run over examples/*.x3         -> 9 clean, 0 runtime failures
```

Each layer proven live on the build path, with its code visible:

```
$ x3c build <intent with a zero-amount swap>
  X3E0501: program[1]: asset move amount must be greater than zero

$ x3c build <fn takes_u64(x: u64) with takes_u64(-1)>
  X3E0202: argument 1 to `takes_u64` has incompatible integer type
```

Two tests pin both, in `test_compiler_pipeline.rs`.

## Why this keeps happening

This is the sixth finding this session with the same shape: a check that exists,
is documented or tested, and is not on the path that matters — silently dropped
warnings, a verifier the build path skipped, an AST-level pass reachable from one
entry point only, an opcode range one reader never learned, a guard whose
quantity no instruction provides, and now two of three pipeline layers with no
caller. It is the dominant debt in this codebase, and it is worth attacking as a
class: TICKET-030 asks for an audit that every `verify_*` pass is reachable from
a real entry point, so the next one is found by a test rather than by its
consequences.
