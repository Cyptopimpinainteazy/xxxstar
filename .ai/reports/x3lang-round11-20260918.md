# X3Lang round 11 — an operand was being read as a payload length

Merged to `origin/master` as `bd0c755b6`, fast-forward from `c1306b929`.
2 files, +60/-6.

## What TICKET-028 actually was

Last round I filed an observation: `x3c explain` reported 4 `REQUIRE` ops and 22
instructions for a bytecode that visibly held 8 `REQUIRE` frames, and I said I
would instrument rather than trust a third hand-count. Doing that resolved it,
and the premise was wrong:

```
program                    IR ops   listed
mainnet_safe_swap.x3           27       28     (+1 for the nonce record)
trading_core_v1.x3              9        9     (no nonce)
internal_swap.x3               13       14     (+1 for the nonce record)
```

The listing accounts for every instruction. My earlier "22" was measured on the
build from the guard-comparison experiment, and that build was genuinely broken —
just not in the way I filed.

## The real defect

`REQUIRE`, `ON_FAIL`, `ON_TIMEOUT`, `ATOMIC_BEGIN`, `ATOMIC_END` and
`ATOMIC_ROLLBACK` are **fixed four-byte frames**: `[opcode][operand_hi]
[operand_lo][pad]`. The walker's `is_payload_opcode` listed all six as payload
opcodes, so it read their operand bytes as a payload length.

That is invisible while the operand is zero — `align4(pc + 3 + 0)` lands on the
same word as a plain four-byte advance, so it looked correct for as long as every
guard was emitted with a zero operand. Give `REQUIRE` `comparison = 1,
threshold = 4` and it reads a length of `0x0401`: the walk jumps a kilobyte past
the end of the stream and every instruction after it disappears from the listing.

## The part worth recording

My hand-written cross-check agreed with the broken walker, because it classified
the same six opcodes the same wrong way. Two independent-looking measurements
that share an assumption are one measurement. The fix for that is not a third
hand-count: it is the count-agreement test added here, which ties the listing to
the emitter's own operation count and cannot share the walker's assumption.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 542 passed, 0 failed
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0
corpus build+verify+run over examples/*.x3         -> 9 clean, 0 runtime failures
```

Two tests added: a four-byte `REQUIRE` with a non-zero operand must not hide the
instruction after it, and emit-then-disassemble over the flagship example must
account for every operation plus the header records.

## Why it matters beyond the listing

This removes the reason I could not emit a real guard comparison last round. The
framing is now handled correctly for all six opcodes, so emitting
`REQUIRE_COMPARE_GE` is mechanically safe. It is still semantically blocked —
no instruction puts a guard's quantity in `r0` — but that is now the only
obstacle, and it is TICKET-027's remaining half rather than two problems
entangled.
