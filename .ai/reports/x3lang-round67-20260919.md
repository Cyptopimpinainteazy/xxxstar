## (b), and the reason it is not merely a name

Reading the two implementations gives something worth writing down precisely: **they
validate two different structures over the same 32 bytes.**

`pallet-cross-chain-validator` accepts an authorized submitter's
`(block_number, block_hash, state_root, merkle_root, proof)` and checks, in Phase 3:

```rust
let leaves = Self::proof_to_leaves(&proof)?;
let recomputed_root = Self::merkle_root_of(&leaves);
ensure!(recomputed_root == merkle_root, Error::<T>::MerkleRootMismatch);
```

a **flat** Merkle tree over 32-byte leaves. There is **no RLP, no keccak and no header
anywhere in that pallet** — `block_hash` and `state_root` are assertions checked only for
being non-zero. `pallet-x3-settlement-engine` then walks an **MPT** receipt proof —
`rlp(index)` as the key, an RLP node path, the receipt as the leaf — against that same
stored root.

So a submitter who attests a block's leaf-Merkle root stores a perfectly valid root and
makes that block impossible to settle, and **nothing complains**: the shape is valid, the
root is stored, and only the trie walk refuses. It is **liveness, not theft** — and that is
exactly why it is stated rather than enforced: there is nothing to enforce against, because
the meaning of the root is the submitter's claim. What the validator pallet *does* check is
that the proof really has the claimed root, so a submitter cannot store a root they cannot
open.

## What is left, recorded rather than implied

- **(a) the SVM binding.** Nothing proves an SVM transaction is *in* the attested slot. The
  router's `SolanaFinalizedVerifier` is an attestation mechanism — a different shape — so
  this needs an account-state or bank-hash proof the workspace does not have. The chain
  **fails closed** meanwhile: `AllowUnboundSvmProofs = false` in `runtime/src/lib.rs`, and
  the mock sets it `true` because the mock stands in for a binding validator.
- **(c) the per-height lookup.** `verify_settlement_evm_header` compares against
  `LastEvmHeader` — one header — while `EvmMerkleRoots` stores a root per height. A
  per-height lookup would let an older block settle, which **loosens** the check. It is a
  liveness improvement, not a security one, and it is not taken without a requirement
  behind it.
- **(d) the test that would make (b) executable.** A runtime-level case where the attested
  root is a flat Merkle root and the walk is refused. It needs the chain runtime's test
  setup, because the settlement pallet's own mock does not include
  `pallet-cross-chain-validator` — **the pallet is not even a dependency of it**. That is a
  real unit of work, recorded rather than half-built.
