# X3Lang round 24 — 2026-09-18 — intent fusion (spec item 21)

Landed on `master` as `5198489de` (base `6fe3b098b`). Spec build-order item 21,
PHASE 21.

## What it does

Intents whose flows close a ring settle against each other instead of each taking
external liquidity: Alice gives ETH and wants SOL, Bob gives SOL and wants USDC,
Charlie gives USDC and wants ETH. `x3c fusion` reports the rings and, per ring,
the five properties PHASE 21 requires: minimum output, deadline, asset
correctness, user authorization, fairness.

```
x3c fusion examples/intent_fusion.x3
  ring alice -> bob -> charlie (assets ethereum.ETH -> ethereum.SOL -> ethereum.USDC)
    authorization: satisfied   asset correctness: satisfied
    minimum output: satisfied  deadline: satisfied   fairness: satisfied
    verdict: fusable — no external liquidity needed for the ringed assets
```

**The consent is in the artifact.** `allow intent_fusion` is a closed feature set
(an unknown name is refused: a permission the compiler guesses at is not a
permission) and it lowers to `FEATURE_ALLOW`, so a runtime deciding whether it may
net an intent against another has something to check.

**Flows come from the lowered operations**, so what a participant gives and wants
is what their intent actually does — the give from its lock, the want from its
release, the minimum from a swap delivering that same asset.

**Every check is three-valued**: satisfied, failed, or *unverifiable with the
reason*. That third value is the design. Whether a ring meets everyone's minimum
needs each participant's minimum and each supplier's amount; a bridge-only intent
states what it bridges and never what it delivers, so its minimum is unknown.
Reporting "satisfied" there would be a ring that looks checked and was not.

**Nothing fuses partially.** If one participant would be handed less than they
required the ring is refused outright — netting that satisfies some and shorts
others is the fairness failure the spec names, and the compiler does not get to
decide who loses.

Rings are bounded, canonicalised to start at their smallest participant, and
sorted, so the report is a function of the intents rather than their order.

## Two mistakes of mine, both caught by running it

- **`Statement::Allow` was parsed and silently dropped.** It had no arm in
  lowering or the formatter and both have catch-alls, so the opt-in vanished —
  consent only the source knew about.
- **I got the frame encoding wrong.** I wrote the feature code as a `u16`, but a
  fixed instruction here is *three* bytes: the reader takes the second as flags
  and the third as the operand's low half. The code landed in the flags byte, the
  operand read as zero, and `x3c run` failed with `InvalidOperand`. The code is a
  byte now, with the constraint written where the constant lives — the same
  three-byte rule that produced the round-22 desync, met from the other side.

## New ticket

**TICKET-038 — a bridge-only intent has no way to state what it delivers.** The
fusion minimum-output check is unverifiable for any intent that bridges without a
swap on the far side, because the language has no `min_receive`. That is the
honest limit of item 21's report, and it is a language gap rather than an
analysis gap.
