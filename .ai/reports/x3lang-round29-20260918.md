# X3Lang round 29 — 2026-09-18 — marketplace metadata (spec item 25)

Landed on `master` as `c120305b4` (base `cb430b515`). Spec build-order item 25,

## What landed

`x3c metadata` emits PHASE 26's document: strategy_id, artifact_hash,
compiler_version, risk_class with its basis, supported_chains, capital minimum
and maximum, effects, required permissions, licence terms, artifact_signature,
receipt_references, notes — "expose metadata without necessarily exposing source",
asserted by a test that the venue name and body statements appear nowhere in the
JSON.

- **The artifact hash is real**: SHA-256 over the emitted bytecode, algorithm
  named in the value. Two builds agree, a body change does not, and a comment
  change does not either — it identifies the artifact, not the file.
- **The two fields a compiler cannot fill are null and labelled.** A signature
  needs a key, and binding one at compile time would make the compiler a signing
  authority; receipt references need history, and a freshly compiled artifact has
  none. Both reasons are in `notes`, because metadata that looks complete and is
  not is worse than metadata that is explicit about its gaps.
- `risk_class` is derived from the declared cost budget at named thresholds and
  reports the numbers it used, so a consumer can disagree with the
  classification rather than with a verdict it cannot see.
- `input … max <N>` is new, and is what makes the capital maximum real rather
  than invented.

A fixture the item-22 check caught: the low-risk test first declared
`max_slippage_bps 10` beside a body relying on `require slippage <= 50`.
Correct refusal, wrong fixture.

## The build order is complete. The spec is not.

The build order's 25 items are implemented and verified. The spec has **56
phases**, and "finish x3lang with all features" is the larger claim. A completion
claim now would be false, so the goal stays open and the next step is an
evidence-based phase audit rather than a keyword sweep.

A first, deliberately crude probe (does a distinctive keyword appear anywhere in
the tree) suggests these phases have no counterpart at all:

| Phase | Probing for | Result |
|---|---|---|
| 15 OBJECTIVE-DRIVEN PROGRAMS | `objective { … }` declaration | absent |
| 29 OPPORTUNITY PACKETS | `OpportunityPacket` | absent |
| 30 DEDICATED EXECUTION LANES | any lane class | absent |
| 38 HYPERARB | any hyperarb primitive | absent |
| 48 ADVERSARIAL TEST MATRIX | a named matrix | absent |

**The probe is not evidence.** Two checks show why: `fixed_point` returns
nothing, yet the trading core does fixed-point arithmetic in integer base units
with per-asset decimals — the concept is implemented under a different name. And
PHASE 49 (fuzzing and property tests) probes to zero for "fuzzing" while five
files use `proptest!`. A phase audit has to look for *behaviour*, not for a word,
which is what the next pass will do: for each of the 56 phases, name the
artifact that would prove it and inspect that artifact.
