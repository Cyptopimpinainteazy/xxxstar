# X3Lang round 30 — 2026-09-18 — determinism and fixed-point, made to hold

Landed on `master` as `28496cd67` (base `c120305b4`).

## What this round was

The phase audit (`.ai/reports/x3lang-phase-audit-20260918.md`) put PHASE 42
(determinism) and PHASE 43 (fixed-point financial math) at "partial, no audit".
Both are *prohibitions* rather than features — no wall-clock jitter, no
randomness, no floating-point ambiguity in anything that moves money — and a
property of the whole tree cannot be proven by one feature's tests. So I read the
tree, found four violations, fixed them, and left the scan behind as a test.

## The four, each a real defect

1. **The production bridge adapter derived its "VRF seed" from the wall clock.**
   `SystemTime::now().as_nanos()`, hashed. Not deterministic, not verifiable,
   reproducible by anyone who guessed the time — and read by nothing, since no
   opcode dispatches to it. It fails closed now, the way the unconfigured adapter
   does, rather than fabricating a value that looks random.
2. **A fractional amount was truncated to an integer.** `expression_to_u128`
   parsed a float literal as `f64` and cast, so `amount 0.5` became 0: a silent
   wrong value in money. It is refused now, and the message names the exact
   conversion that does exist (the trading policy turning `0.02 ETH` into base
   units through the asset's decimals).
3. **A fractional duration was truncated to blocks** — the same shape in
   `timeout_expression_to_blocks`, which I wrote two rounds ago.
4. **A `f64` comparison decided a mainnet rejection.** This one turned out to be
   a units bug, below.

## The units bug the fourth exposed

`semantic.rs` compared the slippage guard's number against `5.0` as a
*percentage*, while `risk.rs` already treated the same number as *basis points*
and the spec writes `require slippage <= 7bps`. So the mainnet check reported
`require slippage <= 50` — a 0.5% guard — as "50% exceeds maximum 5%" and
rejected it: **every program with a slippage guard above 5 bps failed a mainnet
check whose message misstated its own units.** The comparison is in basis points
now, from integer parsing with no float at all, and a test that had been
asserting the old behaviour on `examples/simple_swap.x3` was corrected to assert
the errors that program genuinely earns.

This is the same family as TICKET-033 (timeout unit suffixes accepted and
ignored): a number, a unit, and three different readings of it.

## The scan

`compiler/tests/test_computation_discipline.rs` reads `compiler/src` and `vm/src`
for clock reads, randomness and float code shapes. It found the Solana wire
struct's `warmup_cooldown_rate: f64` on its first run — a legitimate mirror of
Solana's own account layout, which is what the exemption mechanism is for: the
line carries a reason, and adding a float to a money path without one fails the
build. A fourth test asserts the scan actually read the tree, so it cannot pass by
reading nothing.
