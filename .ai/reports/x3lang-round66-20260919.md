## TICKET-082: the 244 errors, and what they were

The crate is `#![cfg_attr(not(feature = "std"), no_std)]` and **already had
`extern crate alloc`** — so it was no_std-aware, and its `std` feature existed only to turn
on `serde/std`, `hex/alloc`, `sha2/std` and the router's `std`. The first two are needed by
code with no `std`-only path:

| class | count |
|---|---|
| `the trait bound String: serde::Deserialize is not satisfied` | 230 |
| `cannot find function hex::encode` | 13 |

Each is a thing the crate does on every path — deserializing `String`s, encoding hex —
gated behind a feature that the runtime's wasm graph switches **off**.
`pallet-x3-settlement-engine` depends on the crate with `default-features = false`, so
"off" is a configuration that has to build.

```
before  cargo check -p x3-crosschain-intent --no-default-features   →  244 errors
after   ...                                                        →  0 errors, 0 warnings
```

The fix is to declare the features where they are needed and let `std` be a switch that
turns something *on*:

```
serde = { ..., default-features = false, features = ["derive", "alloc"] }
hex   = { ..., default-features = false, features = ["alloc"] }
std   = ["serde/std", "sha2/std", "x3-verification-router/std"]
```

## The fail-open the fix uncovered

With the build working, the crate was reachable in a configuration nobody could previously
build — and in that configuration the SVM validator-quorum check did not verify anything:

```rust
for (pubkey, signature) in signatures {
    ...duplicate check, stake lookup...
    // Verify Ed25519 signature
    #[cfg(any(test, feature = "std"))]
    { ...vk.verify(message_hash, &sig)... }
    // no `else`
    signed_stake = signed_stake.checked_add(stake)?;   // counted either way
}
```

Without `std` and not under `test` — the runtime's wasm build — the gate removed the
verification and the loop counted the signer's stake anyway. **A quorum was reached on
stakes whose signatures had never been checked**, so a proof naming any validator and
carrying any 64 bytes would clear the threshold.

The compiler had been pointing at it the whole time:

```
warning: unused variable: `signature`
   --> crates/x3-crosschain-intent/src/proof/svm.rs:164:18
164 |     for (pubkey, signature) in signatures {
```

Fixed by removing the gate: `ed25519-dalek` is `no_std` with `alloc` — the feature set the
crate already declares for it — so the verification runs in both configurations. There is
no acceptable version of this that skips it.

## The test that could not fail, and is why this survived

`verify_quorum_requires_threshold_met` is the one test whose subject is a fake signature.
It asserted:

```rust
assert!(result.is_err() || result.is_ok(), "signature verification should be attempted");
```

`is_err() || is_ok()` is true for every value. Under `std` the result was `Err`; under the
gated build it would have been `Ok`; the assertion accepted both. It now asserts
`Err(InvalidSignature { .. })`, and a new test does the forgery properly:

- a real key, a real validator of the set, and a signature over the **wrong message** —
  well-formed, from a key, and not a signature of this proof — whose stake alone would
  clear a 1/3 threshold, so **nothing but the verification can refuse it**;
- and the honest signature over the right message *does* reach the threshold, so the test
  cannot pass by the fixture being unusable.

That is the fifth instance this session of one pattern, and the most expensive:
`verify_valid_receipt` succeeding against `block_hash = [0xab; 32]`; a `keccak256` test
asserting "not all zeros"; a determinism property generating a one-entry map; a ceiling
assertion satisfied by a parse error; and now a signature test that accepts either outcome.
**Each was a test whose input could not express the property it named.**

## A sweep for the same shape found no others

Every other `#[cfg(any(test, feature = …))]` in this repository gates a **mock**
implementation on `test`/`dev-mock`/`test-utils` — which is the correct pattern, because a
mock must not exist in a production build. This was the only `cfg` gate on a verification.
