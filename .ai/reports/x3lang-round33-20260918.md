# X3Lang round 33 — 2026-09-18 — `x3c fmt` preserves meaning (TICKET-039)

Landed on `master` as `5c8bca061` (base `4984d3dac`). Closes TICKET-039.

## The measurement, before and after

The ticket said `x3c fmt` rewrites valid programs into invalid ones, and gave
intent statements as the example. Measured over the corpus:

| | before (`4984d3dac`) | after (`5c8bca061`) |
|---|---|---|
| examples `fmt` leaves valid | 3 of 17 | **17 of 17** |
| examples `fmt` breaks | 14 | **0** |
| examples the parser cannot read at all | 6 | 6 (TICKET-014, unchanged) |

So the ticket's scope was understated by an order of magnitude, and one of the 14
was worse than the ticket's shape: `on_fail refund arbitrum.USDC to sender` came
back as `on_fail rollback`. The clause folds the asset and receiver into one
string; the formatter wrote that string back as a quoted expression, and the
clause parser reads a quoted string as *not an asset* and falls back to a
rollback. A parse-error test cannot see that. A bytecode comparison can.

## Why it happened, in one sentence

The formatter arms were written against an older grammar and nothing tied them to
the parser, so each clause drifted on its own — `vm` grew a chain name in its
header, `relayers` grew a `quorum: n_of_m` field syntax, `proofs` grew commas,
`rpc_quorum` grew a colon, `risk_policy` and `privacy` grew colons and commas,
`swap` grew its venue before the verb, `error` grew a semicolon, and the intent
body was printed as the `lock`/`release`/`atomic` statements its clauses *lower*
to rather than as the clauses themselves.

## The invariant, stated so it can fail

`compiler/tests/test_formatter_roundtrip.rs` walks the corpus and requires, for
every example the parser accepts:

1. the formatted text parses;
2. it compiles **to the same bytecode**;
3. formatting it again changes nothing.

The second clause is the one that matters and the one a formatter's own tests
cannot replace: it is what proves `refund` did not become `rollback`, and what
proves an `atomic swap` did not lose its amount, hashlock and deadlines. The test
asserts a floor on how many examples it checked, so it cannot start passing by
checking nothing — the failure mode this repo has been bitten by twice.

## Three defects the work exposed in the compiler

- **`finality_policy` lost the chain it was given.** For
  `finality_policy strict { chain ethereum requirement finalized }` the parser
  read `chain` as the chain *name* and `ethereum` as the requirement, then the
  next clause overwrote both — leaving the subject of the IR's finality
  requirement as the literal word `"requirement"` and `ethereum` nowhere. Both
  spellings parse correctly now, and the terse `<chain> require <mode>` form is
  unchanged.
- **`rpc_quorum`'s `require <n>_of_<m>` arm was unreachable.** `require` is a
  keyword, and the arm matched an identifier, so only `require_numerator` /
  `require_denominator` ever did anything. The shorthand has a token to match.
- **`x3c fmt` deleted every comment silently.** The lexer treats comments as
  whitespace, so nothing in the AST holds one, and a formatter cannot write back
  what it was never given. Preserving them needs the lexer to keep them
  (TICKET-043). Until then the command counts them and says what it dropped.

## A correction to round 32's corpus measurement

Round 32 "corrected" the trail's long-standing "16/22 build+run clean" figure,
reporting that `run` was 0 for every example on both `origin/master` and the
branch. That correction was itself wrong, and this round found it while
investigating why `x3c run` apparently failed everywhere.

`x3c run` and `x3c simulate` read **bytecode from a file** — `cmd_run` is
`std::fs::read(input)` followed by `execute_bytecode_verifying`. Round 32's sweep
passed `examples/*.x3` source files to it, and the `X3_VERIFY_FAILED:
OutOfBounds(765)` that seemed to prove a runtime failure is the verifier
reporting the length of the source file it was handed (`examples/simple_swap.x3`
is 765 bytes).

Measured properly — build the example to an artifact, run the artifact:

| tree | files | `check` | `build` | `check --deny-warnings` | `run` (artifact) |
|---|---|---|---|---|---|
| `origin/master` `f44df9e4a` | 22 | 16 | 16 | 15 | **16** |
| this branch | 23 | 17 | 17 | 16 | **17** |

So rounds 28–31 were right and round 32's correction is withdrawn. The mistake is
worth more than an erratum: the round-32 sweep was run against a pristine control
worktree, and the control agreed — **two identical mistakes agree with each
other**. Comparing trees catches regressions, not a wrong command, and only
running the compiler's own advertised usage (`x3c build --out` then
`x3c run <artifact>`) would have caught it.

`/tmp/x3probe/sweep2.sh` is the corrected sweep; `sweep.sh` (the one that produced
the wrong number) is superseded.

## What this round did not do, and the two tickets it leaves

- The 6 examples the parser cannot read at all are untouched; that is TICKET-014,
  and it is a parser/dialect question rather than a formatter one.
- **TICKET-043**: keep comments. `x3c fmt` is now meaning-preserving and still
  documentation-destroying, and for this corpus the comments *are* the
  documentation. The warning makes it visible; the fix is for the lexer to emit
  comment tokens so the formatter has something to place.
- **TICKET-044**: `invariant <name> { assert <expr> }` stores its assertion as
  Rust `{:?}` text (`parser.rs`), so the stored form is not re-parseable X3 and
  the formatter cannot write the body back. No corpus file uses the body form.
