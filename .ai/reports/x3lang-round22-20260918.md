# X3Lang round 22 — 2026-09-18 — multi-VM execution planning (spec item 19)

Landed on `master` as `40ccd1517` (base `ec65b6f12`). Spec build-order item 19.

## What the plan now says

```
PARALLEL_PLAN legs=3;waves=buy_eth,buy_sol|convert_eth;
              edges=buy_eth->convert_eth;
              domains=buy_eth:evm,buy_sol:svm,convert_eth:evm
```

- **Domains come from the program's own declarations** — `vm { chain X adapter Y }`
  and `venue { chain … domain … }`. A chain nothing declares is its own domain:
  the compiler can only honestly report what the program said. Two declarations
  disagreeing about one chain are refused, because the plan would have to say
  which VM runs a leg there and could not.
- **A leg may not cross a chain boundary implicitly.** Moving value between N
  chains takes at least N-1 steps that say so; a leg naming several chains with
  fewer bridge steps is refused, naming the chains. The set of domains a plan
  spans is the answer to "is this multi-VM".

## The defect this exposed

Writing the check surfaced why it had nothing to check: `Operation::Swap` and
`AssetOpPayload::Swap` carried only `from_chain`, and lowering dropped the
output's chain (`to.name`). So `ethereum.DAI -> solana.SOL` lowered to a swap
that looked entirely like an Ethereum operation, and **every cross-chain swap was
invisible to the IR**.

That is exactly why my first version of this feature looked fine: the example I
had just written contained `ethereum.DAI -> solana.SOL` with no bridge, and the
plan reported it as a single-domain leg. With `to_chain` carried through the IR,
the payload encoder/decoder pair, the emitter, both verifiers and the DAG's
read/write derivation, the same program is refused:

```
parallel 'two_way_arb': leg 'buy_sol' touches 2 chains (ethereum, solana) but
contains 0 cross-chain step(s); moving value between chains takes a step that
says so
```

`to_chain` sits after `to_asset` in both the encoder and the decoder; the codec's
trailing-bytes check turns any future asymmetry into a loud error rather than a
silent misread.

## The example was wrong twice before it was right

Both times the compiler was correct and I was not: first it was a chain of three
legs with no parallelism in it to find, then it crossed chains without saying so.
It is now a genuine two-VM plan — an `evm` leg and an `svm` leg in one wave, plus
a leg ordered by an explicit dependency.
