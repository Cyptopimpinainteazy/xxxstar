## The decision, and the evidence for it

TICKET-085 asked for one: wire the register-allocation pass or delete it. It is deleted,
and the reason is not "it was unwired" — it is **what the ISA is**:

| claim | evidence |
|---|---|
| the IR has no operands to allocate | the `Operation` set is economic records — `Lock`, `Swap`, `Bridge`, `Require`, `MultiHopSwap`, … There is no `Operation::Add`, no `Operand::Reg`, and no def/use slot on any variant. |
| so the allocator had nothing to allocate | `compute_live_ranges` computed ranges over temporary ids that no operation declares |
| the VM has no use for an allocation either | its register file exists for one purpose: `REQUIRE` reads `r0`. Operands carry thresholds and constants, not register numbers |
| the author knew | `rewrite_operations` carried `#[expect(dead_code, reason = "v0.2 register allocator placeholder")]` |
| nothing else wanted it | the only references were inside the compiler crate: the module, two re-exports, one entry point, and its tests |

So `patch_operation` was not a rewrite waiting to be written. Wiring it would mean
building a register machine under a language that does not have one, with the artifact's
format changed to carry operand slots — a language redesign, not a wiring job, and nothing
in the phase set asks for it. Meanwhile the public entry point's doc claimed to be "a real
pass in the production compilation pipeline" and its result was discarded, which is the
placeholder the project's rules forbid.

## What was deleted

`compiler/src/regalloc.rs` (four unit tests), the `pub mod`, the two re-exports
(`allocate_registers`, `RegisterAllocationResult`), `compile_program_with_regalloc`,
`compile_program_with_regalloc_str`, and `mod regalloc_wiring_tests` — including the
byte-identity ratchet PHASE 42 added, which did its job: it pinned the pass as a record
rather than a rewrite, and this is the outcome the ticket documented for it.

## A process note, recorded because it nearly cost the round

**Deleting by line range ate the wrong brace, twice.** The first attempt removed
`verify_bytecode`'s closing `}` — the range started at a line I had never asserted. The
file did not compile, and the fix was a restore plus an assertion on the **first** line of
every range as well as the last. The second attempt then caught a wrong *guess* — line 41
is `pub mod risk;`, not what I had assumed — **before deleting anything**, which is exactly
what the assertion is for.

This is the session's own rule ("compute exact line ranges and assert what is at both
ends") being learned again: assert the ends **and** the neighbours, and delete bottom-up,
or the range you computed is not the range you delete.
