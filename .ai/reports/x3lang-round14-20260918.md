# X3Lang round 14 — one funnel for the layers, and an audit that found two more orphans

Merged to `origin/master` as `57202d463`, fast-forward from `1c8c35d59`.
3 files, +202/-158.

## The wiring was the same defect one level up

Last round found two of three documented layers reachable from nothing. Looking
at *how* they were wired showed why:

| Entry point | Checks it ran |
| --- | --- |
| `compile_with_mode` | AST + IR + semantic |
| `check_source_diagnostics_with_mode` | its own copy of the same sequence |
| `compile_program_with_context` | **none** |
| `compile_program_with_regalloc` | **none** |
| `check_source_with_mode` | delegated to the diagnostics variant |

So the layers were wired per entry point, and not the same way in each. Two entry
points produced bytecode with no AST or IR verification at all.

`run_pre_emission_layers` is now the single place that runs them, in one order:
AST-level checks, trading analysis, structural IR invariants, semantic
verification. Every entry point goes through it. A program already refused by an
earlier layer is not lowered, so the caller gets the real reasons rather than a
cascade of consequences. "Every entry point runs the same checks" is now true by
construction instead of something to re-audit after each change.

## The audit, as a test

TICKET-030 asked for a systematic check rather than another inspection. The test
is small and targets the exact failure mode: **every `pub fn verify_*` or
`analyze_*` in the crate must be referenced somewhere outside its own
definition, ignoring comments.** A pass named only in a doc comment is not a
caller — which is precisely what made `verify_ir` look wired while nothing
called it.

It found two more orphans on its first run:

- `semantic::verify_with_defaults` — documented in its own doc comment as the
  entry production callers should use, and called by nobody. `check_ir` was
  making exactly that call by hand; it now uses the function.
- `semantic::analyze_invariants` — a *stringly-typed duplicate* of the same six
  invariant names that `get_builtin_invariants` already implements with real
  check functions, and called by nobody. Deleted rather than left as a second,
  weaker source of truth for the same knowledge.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 549 passed, 0 failed
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0
corpus build+verify+run over examples/*.x3         -> 9 clean, 0 runtime failures
```

Two of last round's tests were corrected, not weakened: they asserted the
*layer label* in the error text ("structural IR", "AST-level"), which the funnel
legitimately collapsed into one message. They now assert the stable diagnostic
code — `X3E0501` for the structural layer, `X3E0202` for the numeric policy —
which proves the same thing and cannot drift with wording.

## The class, one level down

The audit closes the "pass with no caller" case. It does *not* close the case it
now sits next to: `verify_collect` calls its fourteen passes in sequence, so a
pass that is never added to that list is still orphaned in effect while having a
caller of sorts. Filed as TICKET-031 — make the pass list data the funnel
iterates, so both cases become structural.
