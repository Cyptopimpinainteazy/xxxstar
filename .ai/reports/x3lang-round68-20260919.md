## Why a gate and not another fix

Round 66 fixed TICKET-082 (244 errors) and, behind it, TICKET-092 — a
`#[cfg(any(test, feature = "std"))]` around an Ed25519 check with **no `else`**, so in the
configuration the runtime's wasm build uses the verification was removed and a validator's
stake counted toward a quorum anyway.

Both were invisible for the same structural reason: **`cargo check --workspace` builds every
crate _with_ its default features.** A dependency feature the code cannot do without, gated
behind `std` for no reason, is invisible until something turns the feature off — and the
runtime sets `default-features = false` on **64 local crates**, so "off" is not hypothetical.
It is the configuration the chain ships.

So the durable fix is not another one-crate repair; it is building that configuration.

## The gate

`scripts/check-no-default-features.sh`:

- **derives its list** by grepping for the `no_std` posture itself (`#![no_std]` or
  `#![cfg_attr(not(feature = "std"), no_std)]`), mapping each file to its package, keeping
  only workspace members. A crate joins the gate by declaring it can be `no_std`, which is
  exactly the claim being checked. Nothing is hardcoded.
- **checks one crate at a time** — and that is not a detail, it is the whole difference
  between a gate and a decoration. The first version passed every crate to a **single**
  cargo invocation, and it **passed with TICKET-082 deliberately reintroduced**: cargo
  unifies features across a graph, so `hex/alloc` enabled by any other crate in the
  invocation satisfied the intent crate too. Measured both ways:

  | invocation | with the bug reintroduced |
  |---|---|
  | `-p x3-crosschain-intent --no-default-features` | **14 errors** |
  | the same crate via its pallet, `-p pallet-x3-settlement-engine --no-default-features` | 0 |
  | all 64 crates in one invocation | 0 |

  The crate has to be checked alone for its own `--no-default-features` to mean anything.
- **uses each crate's own `alloc` feature when it declares one.** A crate with an allocator
  is not claiming to work without one: `x3-common` fails `--no-default-features` with two
  `String: serde::Serialize` errors and passes with `--features alloc`, so that is the
  configuration it is checked in. This was found by the gate's own second run, and passing
  the feature a crate declares rather than failing it is the difference between a gate and
  a gate nobody runs.

## What its first run found

**5 of 87 crates** declare a `no_std` posture and cannot build that way:

| crate | errors | dominant |
|---|---|---|
| `x3-chain-runtime` | 1 | E0599 |
| `x3-external-chains` | 184 | E0433 ×87, E0412 ×55 |
| `x3-gateway-risk-engine` | 7 | E0412, E0599 |
| `x3-liquidity-core` | 3 | E0599 |
| `x3-sdk` | 216 | E0412 ×147, E0433 ×31 |

They are on a `KNOWN_UNBUILDABLE` list **with their measured counts**, so the gate fails on
anything *not* on it and the list cannot grow silently — a new entry has to be written there,
with a reason, which is the point. The summary prints the known count every run, so it stays
visible rather than becoming a baseline.

TICKET-093 records them with the gate as the validation: **the list must shrink to empty**,
because a crate on it is a crate whose own declaration lies.

## Cost, and where it runs

One cargo invocation per crate: **~13 minutes cold, ~2 minutes warm**. That is why it is in
`GATES_VARIANTS` (opt-in) rather than the fast set, and why the header says so. A gate whose
cost is unknown is a gate that gets removed the first time it is slow.
