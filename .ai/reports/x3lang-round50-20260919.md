# X3Lang round 50 — 2026-09-19 — an invariant body is source text (TICKET-044)

Landed on `master` as `864440a70` (base `627c841dd`). Closes TICKET-044.

## Two defects at one level apart

`parse_invariant_decl_item` stored `format!("{:?}", expr)` for
`invariant <name> { assert <expr> }` — a Rust value tree — and that string is what
reaches the IR (`InvariantCheck.assert_expr`). The formatter could not write the body
back at all, and asking it to would have produced text the parser refuses, because
`format_expression`'s binary arm had the same defect one level down:

```rust
self.write(&format!(" {:?} ", op));    // "Ge", not ">="
```

`BinOp` already implements `Display` with the operator as the language writes it, so
that is `{op}` now, and the parser renders the body with the formatter's own
`expression_to_source` — one renderer, shared, rather than two spellings of one
expression.

```
InvariantCheck { name: "profit_floor", assert_expr: "profit >= 5" }    # was Binary { … }
$ x3c fmt inv.x3 -> invariant profit_floor { assert profit >= 5 }       # re-checks
```

The `assert` keyword is also checked rather than accepted by position: `expect_ident`
took any word there and discarded it, so `invariant x { nonsense profit >= 5 }` parsed.

## Why it stayed hidden

The body form has **no corpus user** — every example writes the bare
`invariant <name>` — so the formatter round-trip test had never formatted a body, and
the binary arm's `{:?}` never appeared in formatted output (guards carry their operator
in a different field). The new test exercises the form for the first time: the stored
text, the formatted text, and bytecode equality between the original and the re-parse.
