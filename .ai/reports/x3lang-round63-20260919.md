## The defect: five examples, `IndexError`, no error surface

```
atomic_choice.x3       list index out of range
objective_routing.x3   list index out of range
opportunity_graph.x3   list index out of range
parallel_dag.x3        list index out of range
strategy_module.x3     list index out of range
```

`_intent_line_index` walks past the last line when a file's every top-level item is a
declaration it skips — which is the whole file for those five, whose subjects are bare
`atomic_choice`, `objective`, `parallel` and `strategy` blocks. It returned that
out-of-range index to `parse_file`, where `lines[start]` raised. **Its own docstring already
said the caller refuses what it does not recognise; the caller did not.**

```
before  IndexError: list index out of range
after   X3_PARSE_NO_INTENT: this file declares no `intent`: this surface reads one intent
        per file, and every top-level item here is a declaration it skips …
```

The neighbouring refusal was wrong in the same direction. A file whose first unrecognised
item is `atomic swap eth.USDC -> sol.SOL {` was refused with `expected intent <name> {`
**at that line** — which sends a reader looking for a typo in a construct that is correct in
the language and simply is not what this surface reads. It now says the file declares no
intent and quotes the line it stopped at.

## The runner had no error surface either

A clean `X3ParseError` — code, message, line, field — escaped `runner.py` as a **Python
traceback**, so the one surface a user actually runs reported a stack where it had a
diagnosis ready:

```
before  Traceback (most recent call last): … cli.X3ParseError: this file declares no `intent` …
after   { "status": "error", "errors": [ { "code": "X3_PARSE_NO_INTENT",
          "message": "…", "line": 58, "field": "intent" } ] }   ← exit 1
```

Same shape as a typechecker failure, so a caller has one shape to read rather than two.

**Where the handler belongs, and why it is not obvious.** The first attempt put it in
`main()` and raised `NameError: name 'cli' is not defined`. The fix is not just to import —
`cli` is loaded **per call** by `load_module`, so a second load gives a *different*
`X3ParseError` class, and an `except cli.X3ParseError` in `main()` would not match the one
the parser raised. The handler is in `run()`, where the same module object is in scope, and
the reason is written at the call site because the next person will reach for `main()`.

## The scope, written down instead of inferred

`cli.py`'s module doc now states four things a reader would otherwise have to discover:
one `intent` per file (every other top-level item is skipped); nine guard kinds of the
compiler's eighteen; an address shape **stricter** than the compiler's; and the rule that
nothing in the module may raise anything but `X3ParseError`.

## A miscount of my own, caught by a gate

The first version of the new runner test used `examples/parallel_dag.x3` as its negative
case. The surface-drift gate — which derives its example list **from this suite's source** —
immediately pulled that file in and failed, because the gate requires the examples the suite
uses to be *readable* and `parallel_dag.x3` is deliberately not. The gate was right to
complain: a test whose subject is "a file with no intent" should write its own fixture
rather than borrow a repository file it is asserting is unreadable. It does now, and the
reason is in the test.
