# X3Lang round 15 — the semantic pass list is data

Merged to `origin/master` as `9ee945db0`, fast-forward from `57202d463`.
1 file, +151/-17. No behaviour change: the same fifteen passes run in the same
order.

## The gap TICKET-030 left open

Round 14's audit catches a pass with **no caller**. It cannot catch a pass that
has a caller of sorts and was simply never added to `verify_collect`'s sequence —
which is where a new pass most plausibly goes missing, because "add it to the
list" is a step you can forget while everything still compiles, tests green.

`verify_collect` called its fifteen passes as fifteen statements. Which passes
exist was only visible by reading that function.

## What changed

The passes are now a table:

```rust
const SEMANTIC_PASSES: &[(&str, SemanticPass)] = &[
    ("verify_symbols", SemanticPass::Symbols),
    ("verify_route_depths", SemanticPass::RouteDepths),
    ...
];

for (_, pass) in SEMANTIC_PASSES {
    run_semantic_pass(*pass, ir, &mut acc, &context);
}
```

An enum rather than `fn` pointers, for a concrete reason the compiler pointed
out immediately: the passes do not share a signature — two take budgets, one
takes the invariant rule set, one is gated on the compilation mode — so a table
of function pointers needs an adapter per pass anyway. With an enum the table and
the dispatch are mutually exhaustive, and a variant cannot exist without an arm.

The test compares the table against the `fn verify_*` definitions in the module,
looking for references **across the whole crate**, because an entry point or an
AST-level pass is legitimately called from `lib.rs` rather than from this file. A
definition that is neither registered nor called anywhere fails.

## The test caught itself first

Its first run flagged four names: two were genuinely unregistered entry points,
and two were **my own test function names** — `fn verify_collect_surfaces_...` —
which is what showed the definition scan had to stop at the `mod tests` marker.
Recording that because it is the second time this session a new check's first
output was mostly about the check: the guard has to be scoped as carefully as the
thing it guards.

## Where the same shape still applies

The VM has the same drift in its reader/executor/verifier trio, and it has cost
three separate findings this session — an opcode range two readers disagreed
about, a header walk two readers disagreed about, and a fixed-frame operand one
reader misread. `vm/src/x3_lang_vm.rs` still has no callers at all (TICKET-026).
The audit shape that worked here — enumerate the published entry points, require
a caller, require every table to be exhaustive — is the obvious next place to
spend it, and it is now written down twice in the tickets so it is not lost.
