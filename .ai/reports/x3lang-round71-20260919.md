# X3Lang round 71 — 2026-09-19 — an executor that reported a success it never executed

Continuation of round 70. Base at the start of the round: `984b9aed6`. Landed on `master`:

| commit | what |
|---|---|
| `f7007ee4d` | `AtomicSwapExecutor::execute_swap_bundle` refuses instead of fabricating a success |

## What TICKET-094's next stop turned up

The pass went to `crates/x3-swap-router/src/atomic_execution.rs`, whose name says an atomic
swap executes there. It has two float sites — and behind them, something worse.

```rust
let gas_used = gas_params.gas_limit;
let slippage_achieved = params.slippage_bps as f64 / 10_000.0;
Ok(ExecutionResult {
    execution_id: H256::zero(),                 // the same "id" for every call
    gas_used,                                   // the limit, not the gas used
    slippage_achieved,                          // the caller's own bound, labelled "achieved"
    execution_time_ms: 10,                      // a constant
    success: !route.hops.is_empty() || params.params.amount_in > U256::zero(),  // always true
})
```

**No swap was executed.** The crate's own test asserted the fabricated success:

```rust
assert!(res.success);
assert!(res.gas_used > U256::zero());
```

A caller that reads `success: true` on an atomic swap bundle believes value moved. This is the
project's own forbidden list — *no-op execution paths*, *placeholder logic* — in a module
named for executing atomic swaps, on `pub` API, and the source said so itself: "Minimal
deterministic execution record; replace with real executor integration".

**Why nothing caught it.** The only caller in the repository is that one test, and no crate
depends on `x3-swap-router` at all — verified by grep. So the no-op path was reachable as
public API and exercised by nothing but the assertion that blessed it.

## The fix

The bundle is refused, with its own variant:

```
error: no swap executor is configured: this router has no chain integration, so it cannot
       execute a bundle and does not report one as executed
```

`SwapRouterError::NoExecutorConfigured` is deliberately not `ExecutionFailed`: a failed
execution is a market outcome and a missing executor is a configuration fact, and a caller has
to tell them apart. The test is renamed
(`executor_refuses_a_bundle_instead_of_fabricating_a_success`) and asserts the refusal, so the
assertion no longer blesses the defect.

**Verified both ways:** with the fabricated `Ok` restored the test **fails**; with the refusal
it passes.

## The float it began as

`slippage_achieved: f64` was `params.slippage_bps as f64 / 10_000.0` — a float fraction of the
caller's *declared* tolerance, named as the slippage *achieved* by a run that never happened.
It is `slippage_bps: u16` now. An execution record has no business carrying a float (PHASE 43),
and a record that echoes the caller's bound under the name "achieved" is a measurement this
crate did not take. The width mirrors `SlippageProtectedParams::slippage_bps`, because that is
what the value is — which my first attempt got wrong by typing it `u32`, and the compiler
caught.

## Two more placeholders, recorded rather than removed

`pub struct SwapBundle;` (a unit struct) and `enum ExecutionStatus { Success, Failed }` are
declared, re-exported from `lib.rs`, and used **nowhere** — not by the crate's tests, not by a
dependent. They are API that exists to look like API. Deleting public API belongs with the
real-integration work rather than in a behaviour-fix commit, so they are in TICKET-094.
