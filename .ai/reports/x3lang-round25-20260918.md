# X3Lang round 25 — 2026-09-18 — a guard's comparison is part of the guard

Landed on `master` as `972b94175` (base `a2bf8c437`).

## The defect

`slippage <= 50` and `slippage >= 50` were the same program. The parser read the
operator and threw it away ("Skip optional comparison operator"), `RequireGuard`
had no field for it, and the IR carried only the number. Measured before the fix:
the two sources lowered to **byte-identical IR**.

That is not cosmetic. `verify_route_fallbacks` compares a fallback's
`require slippage <= N` against what the approved venue declares; `solver_bond`
and `relayer_quorum` compare a guard against a declared bond and quorum. All of
them read a direction, and none of them could tell whether the program had
written one. The checks I built in items 15 and 21 were sound only for programs
written the way I assumed.

## The fix

- `RequireGuard.comparison: Option<ComparisonOp>`; `None` is a guard that
  asserts a property rather than a threshold (`require nonce unused <id>`).
- Parser parses the operator; formatter prints it.
- `Operation::Require` carries it, and the emitter packs it into the `REQUIRE`
  flags byte: bits 0-1 remain the comparison *mode* (should the VM test a
  run-time quantity), bits 2-4 are the guard's own operator. The executor masks
  the mode bits before reading them — without that, `require slippage <= 50`
  arrives as comparison code 8 and is refused as unimplemented. Both verifiers
  validate the byte.
- The three direction-dependent checks assert their direction: bond and quorum
  must be `>=`, a fallback's slippage bound must be `<=`. A guard written with
  the wrong direction is refused with a message saying so.

Measured after: `<=` reaches the IR as `LessOrEqual` and `>=` as
`GreaterOrEqual`; the corpus is unchanged at 15/21 build+run clean and 14
warning-free, so no guard changed meaning in practice; `x3c fmt` now prints
`require finality.arbitrum >= 32` rather than `require finality.arbitrum 32`.

## New ticket: TICKET-039 — `x3c fmt` rewrites valid programs into invalid ones

On an intent it emits `lock …` / `release …` / `atomic { … }` at intent-body
level, and the intent body accepts only `from`, `to`, `route`, `require`,
`timeout`, `on_fail`, `use`, `on`:

    x3c: parse error: unexpected clause in intent body: KwLock; expected one of
         `from`, `to`, `route`, `require`, `timeout`, `on_fail`, `use` or `on`

It also splits `on_fail refund X to sender` into three statements and prints
`uniswap swap …` with the venue and the keyword transposed. The strategy
formatter inherits the same statement arms, so `x3c fmt` is not yet safe to run
on the new module surface either.
