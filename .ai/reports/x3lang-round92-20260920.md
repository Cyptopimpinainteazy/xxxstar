## TICKET-098 — `dd07b0bc5`

`Statement::While` lowered with `let _cond_ir = expression_to_condition(cond)?;` — the guard was
parsed, converted and thrown away, so the IR carried `Loop { max_iterations: 1000 }` and nothing
saying what the loop tested, and the refusal both the verifier and the emitter raise could not
name the guard it was refusing.

| measurement | before | after |
|---|---|---|
| `x3c lower` of `while steps < 10 { … }` | `Loop {max_iterations: 1000}` | `Loop {max_iterations: 1000, condition: Expression {expr: "steps < 10"}}` |
| `x3c build` of the same | refused: `` `loop` cannot be executed — … no target it could jump back to `` | refused: `` `loop` over `steps < 10` cannot be executed — … and no instruction that puts its condition in a register `` |
| `x3c build` of `while 1 > 2 { require profit >= 9 }` | refused | `108 bytes (27 ops)`, byte-identical to the same program without the loop |
| `x3c build` of `while true { … }` | refused as `` `loop` `` | refused as `` `loop` over `true` `` — decided, and still not dropped |

Two rendering defects fell out of the same work, in the shared `expression_to_string`: a binary
operator printed with `{:?}` (`steps Lt 10` — a guard the program never wrote), and a unary
expression falling through to `{:?}` (`Unary { … }`). `BinOp`/`UnOp` already implement `Display`
with the language's own symbols.

Gate tests: `compiler/tests/test_loop_condition.rs` (4) and a rewritten `test_ir_verifier.rs` pair
(one asserts the guard is named, its sibling asserts a decided-false loop is *not* refused).

## TICKET-097 — `d7b6cba9e`

The version byte did not move with the opcode set. Before/after on a real artifact with one byte
changed, old binary vs new:

```
BEFORE  x3c explain gate_v2.x3b     →  "; x3-lang bytecode v0x02" then a full disassembly
        x3c explain gate_op.x3b     →  "0001  0x03  UNKNOWN" then the walk continued
        x3c run     gate_v2.x3b     →  X3_VERIFY_FAILED: OutOfBounds(32)      (a shape error)
AFTER   x3c explain gate_v2.x3b     →  "the artifact states bytecode version 2, and this reader
                                        knows version(s) [1]: … refused rather than walked"
        x3c run     gate_v2.x3b     →  X3_BYTECODE_VERSION_UNSUPPORTED: … version 2 …
        x3c explain gate_op.x3b     →  "at pc 12: opcode 0x03 is not in this format's opcode set"
        x3c run     gate.x3b        →  ok — 1 asset ops, 0 bridge ops, 0 receipts, gas remaining 999368
```

What was decided, in `spec/opcodes.rs`, where a format change will read it:

- `OPCODE_SET: &[(u8, u8)]` — 86 entries, every opcode with the version that introduced it.
- **The gate is the compiler's, not a test's**: `const _: () = assert!(CURRENT_BYTECODE_VERSION ==
  max_opcode_version(), …)`. Registering an opcode at a version the writer does not write produces
  `error[E0080]: evaluation panicked: the version byte this pipeline writes is not the greatest
  version in OPCODE_SET …`.
- `is_defined_version` (framing) and `is_supported_version` (compatibility) are asked in that
  order; the two `has_compiler_header` copies now use the first, so a version-2 artifact reaches
  the verifier to be refused instead of being walked as raw bytecode.
- `version_refusal` and `opcode_version_refusal` word both refusals once; the compiler's walker,
  the trading decoder and the VM's verifier render them. The VM's verify failure now uses `Display`,
  so `x3c run` shows the sentence (the variants without a reason fall back to their `Debug`
  spelling inside `Display`, which is why no existing message moved).
- The VM's range-based `valid_opcode` is **deleted**: it accepted every unassigned byte in
  `0x00..=0xAB`, so the verifier passed what the executor refused one instruction later.

Four mutations prove the new tests are load-bearing: dropping `VENUE_SETTLEMENT` from the registry
fails the source-walk gate by name; registering an opcode at version 2 fails the build; making
`version_refusal` return `None` fails the version test; making `opcode_version_refusal` return
`None` fails the opcode test.

## What was found and recorded, not fixed

- **TICKET-105** — the gate asserts a *global* maximum, so the first version-2 opcode will make
  every new artifact carry version 2. A per-artifact reading (the greatest version among the
  opcodes an artifact contains) may be the right shape; the two doc sentences that state the policy
  must agree whichever way it goes.
- **TICKET-106** — TICKET-058's remainder, now *scoped*: branch mechanics are sound (every
  instruction starts at a multiple of four; `IF` skips four-byte units, so a skip is
  `body_bytes / 4`), and what is missing is a value in a register — there is no immediate-load
  instruction and no arithmetic codegen. The smallest real step is a measured-branch instruction at
  version 2, which TICKET-097's gate now makes safe.
- **TICKET-107** — `base_gas_cost` says `0x0A` is "no instruction in this catalogue" while
  `executor.rs`'s first arm executes `0x0A` as `POW_RRR`.
- **TICKET-108** — `test_control_flow_e2e.rs` contains `assert!(result.is_ok() || result.is_err())`,
  an assertion that cannot fail.
