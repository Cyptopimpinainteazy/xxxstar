## Where it came from

`/root/arb_ir` re-audited `crates/x3-crosschain-intent/src/proof/evm.rs` and found
the same thing TICKET-065 already recorded, with a call-site sweep behind it:

- `compute_receipt_trie_root(receipt_rlp, _index, _total_receipts)` used neither
  underscore parameter and returned `keccak256(rlp(receipt))` — the hash of the
  caller's own bytes, presented as the root of the receipts trie.
- `block_hash` was copied into the result and otherwise never read.
- `tx_hash` was `[0u8; 32]`, `confirmations` a hardcoded `1`.
- `TrieRootMismatch`, `ReceiptHashMismatch`, `InsufficientConfirmations` and
  `InvalidReceiptIndex` were declared and **never constructed**. Measured, not
  eyeballed:

```
$ for v in InvalidReceiptIndex TrieRootMismatch ReceiptHashMismatch InsufficientConfirmations; do
    printf "%-26s " "$v"; grep -c "EvmProofError::$v" src/proof/evm.rs; done
InvalidReceiptIndex        0
TrieRootMismatch           0
ReceiptHashMismatch        0
InsufficientConfirmations  0
```

- `proof/mod.rs` claimed "the intent compiler's `VerifyProof` instruction calls into
  this module through the `ProofVerifier` trait". `ProofVerifier` appears exactly
  once repo-wide — in that comment.
- `verify_valid_receipt` asserted success against `block_hash = [0xab; 32]`, a root
  that holds nothing. The tests *pinned* the defect, which is why the doc claim
  survived.

## What changed

Delegation, not re-derivation. `verify_evm_receipt_proof` now takes `receipts_root`
and `trie_proof` and calls
`x3_verification_router::evm_receipt::verify_merkle_patricia_proof` — the canonical
verifier, already wired to the relayer — with
`evm_receipt::receipt_trie_key(receipt_index)` as the key and the caller's receipt
RLP as the leaf value.

Using the router's own key helper is deliberate: TICKET-064 was the router's key
being `rlp([index])` instead of `rlp(index)`, and a second crate that derives the
key itself can re-derive that bug. One home.

The rest is subtraction and honesty:

- `compute_receipt_trie_root` deleted; `rlp_encode_bytes` / `rlp_encode_list`
  demoted to `#[cfg(test)]`, because their last lib caller was that root.
- The four never-constructed variants are gone, replaced by `NotIncluded` — which
  the walk actually produces — and `NoHeaderAttestation`.
- `block_hash`, `tx_hash` and `confirmations` are `Option`s.
  `with_header_attestation` records a chain view as an *attestation*;
  `require_confirmations` refuses with `NoHeaderAttestation` when there is nothing
  to measure against, rather than reading the old default of `1` as one
  confirmation.
- The `keccak256` doc said "Uses SHA-3 with 256-bit output (same as Ethereum
  keccak256)". `sha3::Keccak256` is the right primitive, but it is not FIPS-202
  SHA3-256 and the distinction is the entire hash. The test beside it asserted only
  "not all zeros" against a `Verified:` comment whose value is the digest of
  nothing; it is now a known-answer test of `keccak256("")` =
  `c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`. That test
  passing is also what confirms the primitive choice is Ethereum's.

## The proof that makes this more than a rename

The tests build a real one-leaf receipts trie from the **standard** encoding rather
than from anything the verifier exposes:

```
key   = rlp(index)                                  (index 0 -> 0x80, index 7 -> 0x07)
node  = rlp([ compact_leaf_path(nibbles(key)), receipt_rlp ])
root  = keccak256(node)
proof = rlp([ rlp(node) ])
```

A green positive test therefore means the delegation works end to end. Four
failures that could not previously be *expressed* are now tests:

| test | what it pins |
|---|---|
| `a_tampered_trie_node_is_refused` | one flipped byte in the node → `NotIncluded` |
| `a_receipt_at_the_wrong_index_is_refused` | root holding it at 7, claim of 0 → `NotIncluded`; claim of 7 → ok |
| `a_receipt_under_a_root_that_does_not_hold_it_is_refused` | a root from a *different* receipt → `NotIncluded` |
| `an_empty_proof_list_is_refused` | `0xc0`, a proof that walks nothing → `NotIncluded` |

The third is the one the old code could not fail: it hashed the caller's bytes, so
every root the caller named was "confirmed".

## Found while validating, recorded not fixed

`cargo check -p x3-crosschain-intent --no-default-features` fails with **244
errors**. `default = ["std"]` and `std = [..., "hex/alloc", ...]`, while the crate
calls `hex::encode` unconditionally — so switching the default features off removes
an API the code always uses, and this crate's `no_std` path has never been built.
It is latent rather than live because `pallet-x3-settlement-engine` uses default
features, but it is not hypothetical: the root workspace already carries a note
about a `blake2`/`std` path leaking into `wasm32v1-none`, so this class has shipped
here before. Measured rather than assumed — moving `hex`'s `alloc` feature to an
unconditional `features = ["alloc"]` takes 244 to **231**, which is why it is
TICKET-082 and not a line in this commit.

## Residual risk of this change

Adding `x3-verification-router` to `x3-crosschain-intent` enlarges the dependency
tree of a crate that `pallet-x3-settlement-engine` depends on, and the router pulls
`scale-info` and `x3-bitcoin-vault`. The pallet's native build is verified above;
the `wasm32v1-none` build of the pallet was **not** exercised in this environment,
so the size and feature-unification effect is unmeasured. The router is
`no_std + alloc` and its own crate is already a workspace member compiled into the
runtime graph, so the expectation is that this is safe — but it is an expectation,
and it is recorded here as one.
