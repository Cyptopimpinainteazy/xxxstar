Landed on `master` as `d6b0fd85c`, `f33b5ecab`, `521593b77` and `4984d3dac` (base `f44df9e4a`).
Closes PHASE 15's surface and, in landing it, two checks that were not on the

## What PHASE 15 asked for, and what was there

`objective { maximize net_profit; constraints { hops <= 3 risk <= 0.4 } }` — what
a program is asking the planner to do, declared in the program rather than passed
on a command line, with two requirements that shape it:

- **"Multi-objective optimization must be deterministic."**
- **"Do not allow non-deterministic solver output to affect consensus."**

Nothing existed: `ObjectiveDecl` and `objective {` appeared nowhere, which the
phase audit recorded as `absent` with `[now]` evidence at round 30. The planner
existed and took its objective from `x3c optimize --objective`, so the phase was
about moving that decision into the artifact and making the compiler answer for
it.

## The declaration

`crates/x3-ast/src/ast.rs`: `ObjectiveDecl` with a `Symbol` name, an
`ObjectiveMetric` and `ObjectiveConstraints`.

- **Direction is part of the metric.** `ObjectiveMetric::direction()` and
  `name()`, not one keyword: `maximize fees` is a mistake about a known word
  rather than an unknown word, and the message says which direction the metric
  has. This also removed a formatter defect before it shipped — the first cut
  wrote `minimize <keyword>` for every metric, which would have rewritten a
  `maximize` into a `minimize`.
- **All nine metrics parse; four are refused with their reason.** The four the
  opportunity graph has no quantity for — profit, output, external liquidity,
  capital efficiency — are refused by `criterion_for` *with an explanation*,
  because accepting them would leave the ranking to whatever solver ran, which
  is the thing the phase forbids. The refusal set and the optimizer's set are
  asserted to line up in both directions.
- **Constraints**: `hops`, `chains`, `risk` (a score or `strategy.policy`),
  `execution_time`, `fees`, `slippage`, `finality`, `capital <= N <ASSET>`,
  `private`, `atomic`. Units are optional and written for the reader; a *wrong*
  unit is refused by leaving it unconsumed (so it becomes an unknown clause), and
  an *attached* unit (`2_000ms`, which the lexer reads as one word) is refused by
  name with the spelling to write instead. The previous cut accepted an attached
  suffix it did not understand and produced "venue execution_time must be an
  integer literal" from a venue-named helper.
- **Keywords that are also words.** `slippage`, `finality`, `risk`, `profit` and
  `atomic` are lexer keywords, and `atomic` has a token of its own. A first cut
  read constraint names with `expect_ident`, which refused every legal objective
  that mentioned one of them; `peek_word` reads the word either way.

## Two checks that were not on the path

Both were found by wiring the declaration to the search — the shape this session
keeps meeting.

**`OpportunityConstraints::max_fee_bps` was never enforced.** A fee bound is a
sum over a path, so it cannot be answered one edge at a time, `reject_reason`
only answers for edges, and no path-level check existed. A caller could set a fee
ceiling and have *every* route go through it, ranked as though the bound were a
preference. `path_reject_reason` now answers for the path (fee total, chain
count, hop count) and the search asks it of every path it extends. The CLI now
shows the difference: the example's `max_total_fee_bps 8` removes the 9 bps route
— `considered 2 route(s)` before, `1` after.

**`risk <= strategy.policy` compared a slippage ceiling to a risk score.**
`StrategyRisk` declares `max_slippage_bps` and `max_total_fee_bps`; the clause
was setting `max_risk` — a venue's 0–100 risk figure — to the profile's slippage
bps. Those are different quantities. The profile's two ceilings are now what the
clause becomes, tightened against anything the objective states, and `max_risk`
is left unset rather than invented from either.

## Reachability

A declaration that verified and did not reach the planner would be a check that
exists and is not on a path, so `x3c optimize` follows it:

```
$ x3c optimize examples/objective_routing.x3 --from ethereum.USDC --to solana.SOL
x3c optimize: minimize_fees (declared by objective 'cheapest_route')
  wide_pool -> x3_bridge  (6 bps fee, 21 bps slippage, risk 4, 914ms, 32 block(s) finality)
  within 3 hop(s), considered 1 route(s); the objective decided
```

The metric, the hop bound and every ceiling come from the declaration, and the
output names the objective it followed. `--objective` and `--max-hops` still
override — a flag is an instruction about this run — but a flag that
*contradicts* the declaration is refused rather than silently preferred, because
the compiler follows one of the two rankings and a caller that believes it
followed the other has been misled:

```
$ ... --objective minimize_slippage
x3c: the program declares objective 'cheapest_route' (minimize fees), and
--objective says minimize_slippage; the compiler follows one of them, so drop
whichever is wrong
```

`--max-hops 1` overrides and then correctly finds nothing:
`no route from ethereum.USDC to solana.SOL within 1 hop(s)`.

## Refusals, and what they say

| written | refused because |
|---|---|
| `maximize profit` / `maximize output` / `minimize external_liquidity` / `maximize capital_efficiency` | `the opportunity graph holds venue attributes, not amounts or prices, so the optimizer cannot rank two routes by profit; ranking them would fall to a solver, which is what PHASE 15 forbids` |
| `maximize fees` | `'fees' is a metric to minimize, not to maximize; the direction is part of the metric` |
| two metric lines | `objective declares its metric twice; one objective ranks one thing` |
| no metric line | `objective states no metric; an objective that does not say what to rank is a heading` |
| two `objective` blocks | `the program declares 2 objectives (a, b); the compiler follows one, so the rest have no effect` |
| two with one name | `objective 'a' is declared twice; two declarations with one name cannot be told apart in a diagnostic` |
| `objective` over no venues | `ranks routes over a program that declares no venues; there is nothing to rank` |
| `risk <= strategy.policy`, no profile | `no strategy declares a risk profile; there is no policy to bound it by` |
| `risk <= strategy.policy`, two profiles | `ambiguous: 2 strategy modules declare risk profiles` |
| `hops <= 0` | `bounds hops at zero; a route with no hops is not a route` |
| `fees <= 10_001 bps` | `bounds fees above 10,000 bps, which is the whole amount` |
| `capital <= get_amount() USDC` | `requires capital in USDC but states no positive integer amount, so no size can be checked against it` |
| `private` with no submission policy | `requires 'private' execution and no strategy declares a submission policy that provides it` |
| `execution_time <= 2_000ms` | `is written '2_000ms'; a number and its unit have to be separate words, so write '2_000 ms'` |

## Reading the spec, not a summary of it

The first version of this phase was built against the round-30 audit's one-line
description of PHASE 15 plus the previous session's handoff. Reading the phase
text itself (`pasted-text-1.txt` lines 1379–1410) at the end of the round found
**four drifts**, all in the direction of the compiler not understanding a program
written to the spec:

| the spec writes | the first version did |
|---|---|
| `maximize net_profit;` | `unknown objective metric 'net_profit'` — the metric was named `profit`, which is the spelling the phase's *list* uses |
| `execution_time <= 200ms;` | refused the attached unit with "separate words", because the lexer joins `200` and `ms` into one token |
| `capital <= 25_000_000 USDC;` … every clause ends in `;` | accepted, because `;` is optional |
| `objective { … }` — no name | accepted; but every diagnostic said `objective 'objective'` |

Fixed on `521593b77`. Both profit spellings are now one metric, so the spec's
example is *understood* and reaches the refusal the phase's determinism
requirement gives:

```
Semantic error: the objective cannot rank 'maximize net_profit': the opportunity
graph holds venue attributes, not amounts or prices, so the optimizer cannot rank
two routes by profit; ranking them would fall to a solver, which is what PHASE 15
forbids
```

The attached unit is now read and *checked* — `execution_time <= 2_000s` is
refused as a mistake about units, `hops <= 4x` because a count has no unit —
which is the opposite of TICKET-033's defect (a suffix accepted and discarded)
and does not depend on the lexer being fixed first. A test now parses the phase's
block **verbatim**, so this class of drift fails a test rather than waiting to be
found by reading. And two clauses on one constraint are refused: the second used
to replace the first, leaving a ceiling the program wrote in force nowhere.

Two smaller conformance notes, stated rather than implied: the constraint set is
a *superset* of the phase's (`fees`, `slippage` and `finality` are additions, each
one a quantity the graph already ranks), and the metric list is a superset too
(`minimize_finality`). Both are additive; neither changes what the spec's clauses
mean.

## What this round did not do

- `x3c fmt` on the new example corrupts it, because `x3c fmt` still mangles a
  strategy's `execute` block (TICKET-039, evidence added to the ledger). The
  round-trip test therefore uses a strategy-free fixture, and
  `examples/objective_routing.x3` must not be run through `x3c fmt` until that is
  closed. It is not fixed here: the statement arms are shared with the intent
  path, so it is one change, not two.
- `x3c graph` searches with command-line constraints only and does not apply a
  declared objective's ceilings. That is defensible for a raw reachability
  command but it is not said anywhere, so it is TICKET-042.
- The optimizer's second search (the one that reports path-level refusals) can
  exhaust its expansion budget where the first finished, because the path-level
  bounds were pruning it. That is now reported as `BudgetExhausted` rather than
  as "no route" — the honest answer, with a test that builds the case.
- The four refused metrics are refused because the graph has no quantity for
  them. Giving the graph amounts and prices would let `maximize profit` be
  answered — that is a larger change than a phase, and the refusal is the honest
  position until then.
