## 1. TICKET-094, third stop — `crates/x3-dex/src/amm_pools.rs`

The ranking this ticket has been walking put this file first: six lines that name money *and*
perform a float operation. Reading it end to end found **nine** functions doing it, not six.
`preview_swap` was the one the enumeration missed, which is the whole failure mode of a
line-counting worklist and the reason the fix includes a test that pins preview against
execution.

Every one of these priced something a caller then treats as money, in `u128`:
`add_liquidity`, `remove_liquidity`, `swap`, `calculate_lp_for_deposit`,
`add_liquidity_calculate`, `remove_liquidity_calculate`, `swap_calculate`, `lp_for_deposit`,
`preview_swap`.

**The defect.** `10^24` is not representable as an `f64`:

```
float(10**24) == 999999999999999983222784   # 16.8 quadrillion units short
```

A pool holding `10^24` units was quoted against reserves that are not the reserves it holds.
Measured at reserves `10^24`, a `10^18` swap, 30bp fee:

```
exact integer form : 996999005991991025
float form         : 996999005991991040     (15 units too generous)
```

The float form was not merely imprecise, it was *inconsistent*: constant product is a floor
operation, and `f64` rounded the quotient **up**. Run against the float implementation the new
exactness test fails with `left: 996999005991991040, right: 996999005991991025`.

**The fix** is four shared helpers rather than nine copies of one formula:

- `mul_div(a, b, d)` — `a * b / d` through a 256-bit `sp_core::U256` intermediate, so
  `reserve * net` cannot wrap the `u128` it computes in; `None` on a zero divisor.
- `net_of_fee(amount_in, fee_basis_points)` — the input a swap actually prices.
- `swap_out(...)` — the constant-product rule, one implementation, `Result`.
- `lp_for_deposit(...)` — the proportional-share rule, one implementation.

`add_liquidity_calculate`'s ratio check now cross-multiplies in `U256` instead of dividing two
floats and comparing quotients.

Three tests, each written to fail on the old code: `a_swap_at_a_realistic_size_is_exact`,
`a_swap_never_decreases_the_product`, `preview_swap_agrees_with_swap`.

Public signatures are unchanged — this is a numerics fix, not an API change.

## 2. TICKET-095 — an amount with no `float` representation ran to completion as `NaN`

`x3-lang/numeric.py`'s `parse_decimal` rejected what `Decimal.is_finite` rejects. All nine of
its callers narrow the result on the next line:

```
simulator.py:48   planner.py:39,85   runner.py:57,63,85,87   typechecker.py:72,137
                                                 -> float(parse_decimal(...))
```

and `float()` does not raise on a `Decimal` outside its range — it returns `inf`.

Before (`intent overflow { from ethereum.USDC amount 1e400 ... }`, run against HEAD's sources
extracted with `git archive`):

```
exit 0
"estimated_slippage_usd": Infinity,
"expected_profit_usd": NaN,
"status": "rolled_back"
```

A run that ended `rolled_back` on `NaN` profit. `json.dumps` writes `Infinity` and `NaN` and
RFC 8259 defines neither, so **the runner's own output document stopped being JSON** — and
nothing raised at any point, so nothing said so. Verified: a strict parse of the before-document
refuses with `Infinity`.

After:

```
exit 1
{"code": "X3_INVALID_AMOUNT",
 "message": "amount must be positive numeric (value must be finite)",
 "field": "from.amount", "value": "1e400"}
```

The check goes in `parse_decimal` — the one place all nine callers pass through — not at nine
call sites. The bound is the pipeline's own representable range, not a ceiling on how large an
amount may be: `1.7976931348623157e308` is still accepted, `1e309` is not.

The message names the rule that was broken. `1e400` *is* positive and it *is* numeric, so the
old `"amount must be positive numeric"` sent its reader to the sign and the spelling while the
defect was representability.

**Also in this commit, and labelled differently:** `runner.rust_intent_envelope` and `run` read
`requires`/`policies` with two-argument `get`, whose default applies only when the key is
*absent*. The typechecker decides that null means absent — it normalizes `policies is None` to
`{}` itself — so a validated intent carrying `"requires": null` crashed the consumer that had
just blessed it (`TypeError: 'NoneType' object is not iterable`), and the envelope handed the
compiler a `requires: null` its serde `Vec<Requirement>` refuses. `cli.parse_file` cannot
currently emit either, so this is **contract consistency, not a live crash**, and it is tested
as the contract it is rather than claimed as a reachable defect.

## 5. TICKET-094's missing artifact — reachability of the 84-line worklist

The ticket's acceptance criterion is a **classification**, not a pile of conversions, and the
classification has to answer "does this reach a balance/reward/slash/settlement decision?"
before it answers "is this float?" — because a float that nothing calls is not a defect. The
first step of that, measured rather than assumed, is whether the containing crate is on any

*least*: its two float sites are in `get_price_decimal` and `get_price_change_pct`, both of

decides whether a price is an anomaly — has **no call sites at all, including its own tests**.
Converting them would have been polish on code the build does not compile. Recorded as
TICKET-096 rather than fixed.

## 6. `a61aa8bbf` — the arb spread, in the crate the classification said was reachable

`ArbBotEventSystem::detect_opportunity` computed
`((price_a - price_b) as f64) / (price_b as f64) * 10000.0 as u32` and that number both
decided admission (`if spread < 10 { return Err(...) }`) and was stored as `spread_bps`.

**Measured, two consequences.** (1) An exact 12 bps — `lo = 10^15`, `hi = lo + 1.2*10^12` —
stored as **11**: both `u128` casts round above 2^53 and the quotient lands under the integer
the inputs state. 195 such (t, k) pairs exist in the family `lo = 10^4 * t`, `hi = lo + t * k`.
(2) The `as u32` **saturated**, so `u128::MAX` against `1` — 3.4e42 bps, two prices in
different units — was *admitted* carrying `spread_bps: 4294967295`, the most attractive trade
the field can express.

What was **not** found, and is therefore not claimed: in that family and in 800k random pairs,
the one-bps error never crossed the `spread >= 10` boundary. A wrong number, not a wrong
decision. The test says exactly that.

Both tests were verified failing against the restored `f64` expressions (`left: 11, right: 12`
and `Ok(... spread_bps: 4294967295 ...)`). `update_performance`'s win-rate accumulation was
converted too — it is a statistic, not a decision, so it is recorded as a simplification and
not counted as a defect fix.
