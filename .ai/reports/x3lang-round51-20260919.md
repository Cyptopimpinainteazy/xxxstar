## 1. A fixed frame is three bytes, or four for `REQUIRE` (TICKET-057)

The emitter writes a fixed instruction as `[opcode][flags][operand]` — three
bytes — and then pads the buffer to the next absolute multiple of four.
`REQUIRE` is the exception: it writes `[opcode][flags][threshold u16]`, four
bytes of content. Every reader assumed three.

The two widths round to different boundaries exactly when a frame starts at an
offset congruent to one mod four, which is where the first instruction of a
compiler stream without metadata sits, because byte zero is the version byte:

```
align4(1 + 3) == 4        # a three-byte frame: the padding byte completes it
align4(1 + 4) == 8        # REQUIRE: the frame itself crosses the boundary
```

So a program whose first instruction is a guard was walked one byte into the
guard's own operand and then onto its padding. Measured on a six-instruction
program whose first item is `risk_policy`:

| reader | before | after |
|---|---|---|
| `x3c explain` | 18 lines, mostly `UNKNOWN` | the 10 instructions, in order |
| verifier boundaries | 10 offsets for 9 instructions (the padding was one) | 9, the emitted set |
| executor dispatches | 10 | 9 |

Fixed by making the width one table in `spec/opcodes.rs` — `fixed_frame_content_len`
and `fixed_frame_operand` — read by the disassembler, the verifier and the
executor, and adding a helper that reads a fixed frame's operand at the width the
frame carries. Three-byte frames in a compiler stream store only the operand's
low byte; the high byte is the padding, and at offset 1 it was the *next*
instruction's opcode. A leading `feature_allow` would have presented itself as
feature code 0x5683 and been refused by the VM as one the language does not
define.

Tests: the emitter asserts the walk visits exactly the IR's operations for a
guard-first and a payload-first program (and that no `UNKNOWN` appears); the VM
asserts the verifier's boundary set equals the emitted operations and the
executor dispatches one instruction per operation. Against the old advance the
VM test fails with `{1, 4, 8, ...}` — ten boundaries for nine instructions.

## 2. `finality` has a declared depth (TICKET-049, finality)

Twelve guards in nine corpus programs compared a chain's settlement depth against
a quantity nothing declared, so each lowered to a `REQUIRE` the executor treats
as true. `finality_policy` gained the clause that answers them — `blocks <n>` —
along with a compile-time check in `semantic::verify_finality_guards_declared`:

- a depth guard **below** the declared depth is refused with both numbers: it
  would pass at a depth the program's own policy says is not final;
- a depth guard at or above it is accepted (stricter is more conservative);
- a mode guard (`== finalized`) is decided against the declaration's
  `requirement` word, case-insensitively;
- a guard naming a chain no policy declares, or a policy that states no depth,
  is refused with the clause to add;
- two policies naming one chain are refused where a guard depends on them.

`examples/` and the compiler's own fixtures now declare what their guards
require, generated from the guards themselves so no number is invented. 11 new
tests in `compiler/tests/test_guard_declarations.rs`, including a corpus
invariant over every example that writes a finality guard.

## 3. The Python harness reads a file that declares before its intent

`cli.py::parse_file` required line 0 to be `intent <name> {`, so a file with any
leading declaration was unreadable — one example gaining a `finality_policy`
block failed thirteen pytest tests, none of them about finality. A leading
declaration is now skipped as a whole (header plus brace-balanced body), with a
refusal if the body is never closed, and anything that is neither a declaration
nor the intent still fails loudly.

## 4. Settlement engine: a proof is verified against roots it carries

`pallets/x3-settlement-engine/src/lib.rs`, both cross-chain sites, read the two
roots they verify against with `first().copied().unwrap_or_default()` and
`get(1).copied().unwrap_or_default()`. `unwrap_or_default()` on an `H256` is
thirty-two zero bytes, so a proof carrying fewer than two `merkle_proof` entries
was verified against roots it never stated. The EVM site's closing
`valid && !proof.merkle_proof.is_empty()` was the author reaching for this check
and getting the length wrong — non-empty is one entry; the SVM site had no check
at all.

Both sites now read the pair through one accessor, `proof_roots`, which returns
`None` unless the proof states both, and refuse. The test asserts the positive
case first (the fixture with both roots verifies) and then shortens the list to
1 and 0; against the pre-fix code the 0-entry proof is accepted and the test
fails. `cargo test -p pallet-x3-settlement-engine` → 116 + 23 passed.

The *other* finding — the EVM block number and SVM slot derived from the first
eight bytes of `tx_hash`, so the value that looks up the canonical header is
proof-supplied — needs a decision rather than a patch and is left as a ticket
with the two options in `.ai/reports/settlement-engine-invented-evidence-20260919.md`.

## 6. `x3c fusion` is exercised through the binary (TICKET-015)

The netting module is implemented and the command is wired, but every fusion test
called `fusion::rings` directly — nothing ran the command, so it could have
printed anything and the workspace would have stayed green. That is why
TICKET-015 ("`fusion.rs` is an empty stub") read as open long after the module
was real. Two CLI tests now run the binary: a ring that closes (participants in
order, all five checks stated, the most urgent deadline, a verdict) and the same
ring without `allow intent_fusion` (no ring, no fusable verdict).
