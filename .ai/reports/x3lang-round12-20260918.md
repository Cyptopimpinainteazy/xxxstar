# X3Lang round 12 — a solver bond has to be declared, and the guard is checked

Merged to `origin/master` as `f2b972a3c`, rebased onto the then-current master
after another agent merged PR #282, then fast-forwarded. 9 files, +193/-7.

## The gap

`require solver_bond >= 10000` asserts something about the program's
configuration — that the solver backing the trade has posted at least 10000 — and
the language had no way to say what that bond *is*. The guard was unbacked in the
compiler and in the VM alike: nothing to compare against, so it enforced nothing
anywhere. I named this two rounds ago when deleting the fabricated `SolverBid`,
and it is the concrete instance of "a guard whose quantity has no declaration".

## What landed

`solver_market` gains a bond:

```
solver_market {
    mode competitive
    min_reputation 95
    bond 10_000 USDC
}
```

An amount *with* an asset, the same rule that made `max_gas` need
`max_gas_asset` before it could be enforced. A new AST-level pass checks every
`require solver_bond` guard against the declaration and reports two things: a
guard with no declaration at all, and a requirement above the declared bond.

The intent is that the guard now means what it says. Previously the two
declarations existed in the same file and were never compared — the guard could
require any number at all.

## The gap found on the way

Wiring this up surfaced that the AST-level checks were reachable from **one**
entry point:

```
check_source_diagnostics_with_mode  -> verify_atomic_swap_decls   (x3c check)
compile_with_mode                   -> (nothing)                  (x3c build)
```

So `x3c build` — the path that actually emits bytecode — skipped every AST-level
check, including the pre-existing atomic-swap validation. Both entry points now
run the same `ast_level_errors` helper. This is the same "a check that is not on
the path that matters" shape that has dominated this codebase for the last
several rounds, and it is why the new check went in at a shared point rather
than beside its predecessor.

## Evidence

```bash
cd x3-lang
cargo test --workspace                             -> 546 passed, 0 failed   (542 before)
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check                         -> exit 0
corpus build+verify+run over examples/*.x3         -> 9 clean, 0 runtime failures
```

End to end, with the `bond` line removed from the flagship example:

```
$ x3c build --out /tmp/nb.x3b /tmp/nobond.x3
x3c: compile error: Semantic error: compilation failed with 1 AST-level error(s):
  intent 'safe_cross_vm_swap' requires a solver bond of 10000 but the program
  declares no `solver_market { bond <amount> <ASSET> }` — the guard has nothing
  to compare against
```

and with it present, `x3c build` emits 644 bytes and `x3c run` reports `ok`.

Four tests: unbacked guard rejected, guard above the declared bond rejected,
backed guard accepted, and the build path running AST-level checks.

## What generalises

Every guard kind in the language is a claim about configuration, so the same
shape applies to the rest. `require relayer_quorum >= N` against
`relayers { quorum N_of_M }` is the same check with a different declaration, and
is the obvious next one. `route_score` and `risk` need declared quantities that
do not exist yet. The run-time comparison path stays unused until a guard's
quantity can actually reach its guard.
