# X3Lang round 18 — 2026-09-18 — bounded route fallback (spec item 15)

Landed on `master` as `3328f1c83` (base `5433c9242`). Spec build-order item 15,
PHASE 13 "Bounded Route Mutation".

## What the construct promises, and where each promise is kept

| Spec requirement | Where it is enforced |
|---|---|
| "The runtime may choose only among compiler-approved routes" | the approved list is the payload of `ROUTE_FALLBACK` and is recorded in `VMState.route_fallbacks` |
| "No arbitrary dynamic contract substitution" | the grammar has no wildcard or "any venue" form — an unnameable substitution cannot be written |
| "Every fallback must be statically bounded" | `MAX_ROUTE_FALLBACKS = 8`, one definition shared by compiler and VM |
| substitution is actually checkable | lowering rebuilds the program with the venue in place and runs the same two post-lowering layers |

## Two defects found by smoke-testing, not by compiling

1. **The VM verifier rejected every fallback program.** Its payload validation
   falls through to `decode_capability_payload`, which rejects an opcode it does
   not know, so `x3c run` failed with `X3_VERIFY_FAILED: InvalidOperand` while
   the executor could run the same bytecode. The function already carries a
   comment recording this exact defect for the trading opcode range. Fixed with
   a `ROUTE_FALLBACK` branch that validates its own payload.
2. The `InvalidOperand` pc did not point at the opcode being rejected, which is
   what made the position look wrong at first. Worth remembering when reading
   this verifier's diagnostics: the position is not reliable on its own.

Both would have been invisible to `cargo test` — the new opcode had no
round-trip test until the smoke test forced one to exist.

## The honest limit

The per-substitution check re-verifies the route with the replacement venue in
place, and the only thing that changes is the venue's **name**: no check in the
language reads a venue's properties, because venues have no declared properties
yet. So the check proves "the substituted route is as valid as the original"
and cannot yet catch a venue that is unusable, or more expensive than the
fallback bounds allow. It becomes load-bearing when venues carry declared fees
and liquidity — item 16, the opportunity graph — which is what gives the
`require slippage` / `require profit` bounds something to compare against.

Recorded in the test file as a comment rather than left implied.
