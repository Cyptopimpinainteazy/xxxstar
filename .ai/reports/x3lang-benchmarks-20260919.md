# x3lang performance targets — spec PHASE 50

Measured 2026-09-19 on the machine named in the run below. Generated by building and
running the harness; the table is that run's output pasted verbatim, not a summary of it.

## How to reproduce

```bash
cd x3-lang
CARGO_TARGET_DIR=<a target dir> /tmp/x3lang-cargo.sh build -p x3-tools --bin x3bench
<target dir>/debug/x3bench 2000
```

The harness is `x3-lang/crates/x3-tools/src/bin/x3bench.rs`. Each operation is timed
against the function that actually does it, named in the `exercises` column, so the
claim "this number is the cost of parsing" is checkable rather than asserted.

## What the numbers are

- **Profile: `dev`**, the profile `cargo build` produces. Not `--release`, because the
  phase asks to profile before optimizing and the `dev` profile is where the compiler
  is actually run today; a release run would be a different measurement and is not
  claimed here.
- **Percentiles by nearest rank** over the sorted per-iteration samples, so every
  printed value was observed. With 2000 samples an interpolated p99 would be a number
  that never happened, and a benchmark that reports unobserved values is not a
  measurement.
- Warmup runs precede the samples, so the first-call costs (lazy statics, cold
  allocation) are not in the distribution.

## What this does and does not say

It says where the time goes *in this build, on this machine, over this fixture*. The
one finding worth stating plainly is that **parsing dominates every other operation by
roughly two orders of magnitude** — about 150 microseconds against single-digit
microseconds for the graph, the optimizer and the verifier. Nothing here says the
parser is slow in absolute terms; it says it is the first place to look, and it is the
only operation whose p50 is remotely near a millisecond.

It does not say any of these numbers is acceptable. PHASE 50 asks for the measurements
so that optimization is not blind, and this is the measurement. Deciding targets —
"parsing must be under X" — is a product decision this report does not make, and
inventing one would be exactly the blind optimization the phase warns against.

## Coverage

All ten operations the phase names were measured, including the two the phase lists
separately as "receipt verification" and "economic replay", which are
`trading::verify_receipt` and `trading::verify_receipt_economics` — different checks
over the same receipt, one structural and one re-deriving the traded delta.

The harness exits non-zero if any operation cannot be set up, and prints the reason
under `NOT MEASURED`, so a partial run cannot be mistaken for a complete one. That is
not hypothetical: the first version of this harness reported nine of ten, because its
scheduling fixture built two legs from the same operations and `dag::plan` correctly
refused them as a cycle.
