# X3Lang round 28 — 2026-09-18 — private strategy commitments (spec item 24)

Landed on `master` as `cb430b515` (base `82325398f`). Spec build-order item 24,
PHASE 27 and 28.

## The finding: `privacy { encrypted true }` was an unkeepable guarantee

The executor's `PrivacyCommit` arm reads the flag as `encrypted: _`. So a program
could declare encryption, the compiler accepted it, the artifact carried it, and
nothing anywhere provided or checked it. That is the precise failure PHASE 27
names — "do not invent cryptographic guarantees that are not implemented" — and it
was in the shipped surface: `examples/mainnet_safe_swap.x3` and
`examples/flagship_b52.x3` both declared it. `x3c audit` on the CLI's
fully-configured fixture began reporting `[FAIL] semantic:` as soon as the check
existed, which is the check doing its job on a fixture that had been hiding the
problem.

Declaring it is refused, and the refusal **labels what is implemented** rather
than only what is not:

- **public** (no privacy block) — nothing hidden, every operation visible;
- **hide_route_until_commit true + reveal_on \<event\>** — the route is committed
  to and revealed at the event; the commitment is real (`PRIVACY_COMMIT` is
  emitted and executed), the hiding lasts until the reveal point;
- **submission { private = required }** — the artifact refuses to run without a
  private channel.

`implemented_privacy_levels()` is the single table the refusal and the test both
read, so a level cannot be labelled one way in a message and another in a check.

## The submission policy is enforced, not recorded

`submission { private = required | preferred | allowed }` on a strategy module
lowers to a mode check, and the runtime acts on it. `VMConfig` gained
`allow_private_submission`, defaulting to **false**, so a runtime without a
private channel refuses the artifact:

    X3_PRIVATE_SUBMISSION_REQUIRED: the compiled policy requires private
    submission but this runtime has no private channel

That is the direction the failure has to fall in: an accidental public submission
cannot be taken back. `preferred` and `allowed` are recorded and do not refuse,
because the policy did not ask them to, and the identical bytes run on a runtime
that has the capability.

`ModeCheck` used to validate its two fields and then ignore them, so a policy
that lowered to one was a policy the artifact stated and the runtime ignored —
worse than no policy, because the program believed it was protected.

## Fixtures that carried the claim

Two corpus examples and one CLI fixture declared `encrypted true` so their audits
looked complete. All three now declare only the commitment level, with a comment
saying what was removed and why. `encrypted true` still *parses* — the refusal is
semantic, so the parser's tests of the block are unaffected — and
`encrypted false` claims nothing and is accepted.
