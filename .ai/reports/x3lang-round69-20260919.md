## `x3-chain-runtime`: a feature that had to be on, in `default`

```toml
default = ["std", "tuples-96"]
tuples-96 = ["frame-support/tuples-96"]
```

`construct_runtime!` builds a tuple of the pallets and this runtime has more than the default
limit of them, so the feature is required for the crate to compile **at all** — and
`--no-default-features` turned it off:

```
error: The number of pallets exceeds the maximum number of tuple elements.
       To increase this limit, enable the tuples-96 feature of [frame_support].
```

It is on the `frame-support` dependency now. A feature that *has* to be on for the build to
succeed is not a feature — TICKET-082's `hex/alloc` in a different crate.

**And a measurement correction of my own.** My first reading of this crate said "1 error"; it
was the runtime's **build script** failing, because I ran `cargo check` without
`SKIP_WASM_BUILD=1` — the environment the gate sets. In the gate's environment the crate has
8 errors, all from the tuple limit. **Measure in the same environment the gate does**, or the
number is about a different thing.

## `x3-liquidity-core`: an anti-rug score computed in `f64`

Three places, and the third is why the crate could not be `no_std`:

```rust
((locked_lp as f64) * 10000.0 / (total_lp_supply as f64)) as u16          // a share of supply
((team_wallet_balance as f64) * 100.0 / (total_lp_supply as f64)) as u8   // a share of supply
((lock_duration as f64).ln() * 20.0 / (30.0_f64 * 24.0 * 3600.0).ln()) as u32
```

`ln` is not in `core`, so the crate could not be built without `std` while it used it — and a
platform's `ln` is the platform's, which is PHASE 43's prohibition for a decision of this
kind: **a score built from a float logarithm varies with where it ran.** The build failure
was worth following rather than silencing.

All three are integer arithmetic now. The percentages are exact ratios, with a share too
large to scale scored at the ceiling rather than wrapped (an unrepresentable share is not a
small one). The duration term is `ilog2(d) * 20 / ilog2(30 days)` — the **same ratio**,
because `ln(a)/ln(b) == log2(a)/log2(b)`, computed with no float anywhere.

**What changed, stated rather than implied.** Flooring each logarithm means the duration
sub-score can differ from the float form by at most one point of twenty; the percentages are
now exact where the float form was lossy above 2^53. Pinned ladder:

```
1s   ilog2= 0 ->  0     1h  ilog2=11 -> 10     1d  ilog2=16 -> 15
7d   ilog2=19 -> 18    30d  ilog2=21 -> 20
```

`anti_rug.rs` had **no test module**, which is how a float survived in a security-adjacent
score. It has one now: the ladder, the reachable maximum (a 30-day lock scores 100 — a
maximum a heuristic can never award is a bug in the heuristic), monotonicity in the duration,
and exact shares (half a supply is 5000 basis points, a third 3333, an overflowing scale is
10000).

Writing it found an arithmetic error **in my own expectation** — I had guessed 96 for a
seven-day lock and the code said 98. That is the reason to pin values rather than describe
them.

## The finding beyond it: PHASE 43's scope was narrower than its sentence

Fixing this crate put a float in a *root-workspace* crate, and PHASE 43's audit (round 53)
scanned **`x3-lang/{compiler,vm,crates/*}/src`** — its claim holds within that scope and this
crate is outside it. Measured repo-wide:

```
$ rg -l 'as f64|as f32|: f64|: f32|\.ln\(\)|\.sqrt\(\)|\.powf\(' --glob '*.rs' \
     crates pallets runtime services apps | grep -v /target/ | wc -l
551
```

**551 files.** Not all of them are consensus-sensitive — a simulator, a monitor, an analytics
dashboard and a benchmark may use floats legitimately, and claiming otherwise would be the
over-claim this is meant to avoid. What matters is which compute a value that becomes a
**balance, a reward, a slash, or a settlement amount**. The ones whose names say so, to read
first:

```
crates/x3-staking-analytics/src/{reward_calculator,slash_tracker,staking_ledger,validator_stats}.rs
crates/x3-swap-router/src/atomic_execution.rs
crates/x3-gpu-validator-swarm/src/cpu_validator.rs
```

TICKET-094 records it with the enumeration and the criteria: classify all 551 as "reaches a
balance/reward/slash/settlement decision" or "does not, and here is why", convert the first
kind, and finish with a gate that greps the consensus-sensitive set for float arithmetic —
the same idea as the `no_std` gate, one layer down.
