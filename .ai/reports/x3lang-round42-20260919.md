# X3Lang round 42 — 2026-09-19 — the nonce guard is a check (TICKET-051)

Landed on `master` as `0d22540b6` (base `78f6bb566`).

## The most-used unbacked guard, and the only run-time one

`require nonce unused <id>` appears in fourteen corpus programs. It was the one
guard whose quantity is a *chain* fact rather than a program fact, so it could not
be closed the way the others were (a declaration to compare against): the
identifier reached `metadata.nonce`, nothing consulted it, and the guard lowered to
a `REQUIRE` the executor treats as true. Replay protection was a claim the artifact
recorded and nothing enforced.

## What it took

| layer | change |
|---|---|
| `spec/opcodes.rs` | `NONCE_UNUSED` (0x9C), and in `is_payload_opcode` |
| `crates/x3-common` | `CapabilityPayload::NonceUnused { nonce }` + codec |
| `compiler/src/ir.rs` | `Operation::NonceUnused { nonce }` |
| `compiler/src/lowering.rs` | emit it immediately before the guard (the guard tests `r0`, and nothing else writes it) |
| `compiler/src/emitter.rs` | emit the payload; for this kind only, `REQUIRE_COMPARE_GE` with threshold 1 instead of `STATIC`; disassembler name |
| `compiler/src/verify.rs` | refuse an empty nonce (a replay-protection instruction that protects against no replay) |
| `vm/src/executor.rs` | dispatch arm, gas, memory charge; `r0 = 1` when the nonce is new, and record it |
| `vm/src/x3_lang_vm.rs` | `state.used_nonces: Vec<String>` — what this run has seen |
| `vm/src/verifier.rs` | the same empty-nonce rule, for artifacts the compiler did not build |

That is the first guard in the language with a **real run-time quantity at it**,
which is what TICKET-027's criterion asks for and what the other kinds could only
satisfy by being evaluated. Replay protection is a *host* fact, so the VM carries
the nonces this run has seen (a `Vec`, not a set: every ordering here is explicit so
two runs of one artifact are identical) and a host with a longer memory starts the
VM with the ones it already knows.

`vm/tests/test_nonce_replay.rs` — 4 tests: a fresh nonce passes *and is recorded*,
the same nonce twice fails at the **second guard** (with what it compared), a nonce

distinct nonces are recorded in order.

## The cost of an opcode, and the drift it exposes

Adding the instruction meant touching every place that enumerates payload opcodes,
and two of them are independent statements of the same fact: `is_payload_opcode`
lists opcodes explicitly while the executor dispatches by *ranges*. The first build
verified its artifacts and then failed at run time with `InvalidOpcode(156)` — 0x9C
sits between two ranges. The same shape bit the verifier once before (its
classification omitted `EMIT`/`CALL_HOST` and walked four bytes into them). Filed as
TICKET-055 with a table test as the fix: one source of truth, walked by a test so a
new instruction cannot be added to one list and missed by another.
