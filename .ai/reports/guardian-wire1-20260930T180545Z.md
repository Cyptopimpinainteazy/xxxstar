## Problem

The Independent Guardian audit established that `pallet-x3-app-registry`,
`pallet-x3-security-gate` and `pallet-x3-trust-gate` were workspace members but
were **not** in any `construct_runtime!` block. Every Guardian refusal was a
library statement; on chain nothing could be refused because the pallets did
not exist in the runtime.

```
$ rg -n "app-registry|security-gate|trust-gate" runtime/src/lib.rs      # (before)
(no matches)
```

## Change

`runtime/Cargo.toml`

- Added `pallet-x3-app-registry`, `pallet-x3-security-gate`,
  `pallet-x3-trust-gate` as `default-features = false` dependencies.
- Propagated `…/std` and `…/try-runtime`. The pallets have no
  `runtime-benchmarks` feature, so nothing was added there.

`runtime/src/lib.rs`

- Appended the three pallets to **all five** `construct_runtime!` blocks
  (dev, dev+frontier, mainnet-rc1, default, production+frontier). They are
  appended after the last existing entry in each block, so **no existing pallet
  index shifts** and no storage migration is required (the new prefixes start
  empty).
- Added `parameter_types!` constants (`GuardianMaxApplications` = 10_000,
  `MaxAddressesPerApp` = 16, `MaxVersionsPerApp` = 64,
  `MaxJustificationLen` = 1_024).
- Added `GuardianAuthority`, an `EnsureOrigin<RuntimeOrigin, Success = AccountId>`
  that authorizes exactly like the runtime's other security powers
  (`EnsureRootOrHalfCouncil`) and refuses a bare signer. This SDK's
  `EnsureRoot<AccountId>::Success` is `()` and
  `EnsureProportionAtLeast`'s is `()` too, but the gates record the acting
  account, so the adapter:
  - authorizes via `EnsureRootOrHalfCouncil` (Root or ≥half the council),
  - attributes a signed council-member origin to that member, and
  - attributes Root and motion-enacted calls to `GuardianRootActor`, a
    `PalletId`-derived, non-signer account (`PalletId(*b"py/grdn!")`,
    `into_account_truncating()` — the same idiom as `TreasuryAccountId`).
    `pallet_governance::enact_proposal` dispatches as `RawOrigin::Root`, so Root
    must be accepted or governance could not manage Guardian at all.
- Added `GuardianAuthorityAccountless` (same authority, discards the account) for
  the app registry's account-less `GuardianOrigin`.
- Wired the three `Config` impls. `OwnerOrigin` (registration) stays
  `EnsureSigned<AccountId>` — registration is permissionless by design (spec §4)
  and an EXPERIMENTAL application inherits no privileges.

`runtime/src/tests.rs`

- New test `the_guardian_gates_are_wired_and_refuse_an_unprivileged_caller`. It
  asserts the three pallets are in the runtime's `PalletInfo` (membership, not
  just callability), then drives them **through the real `Runtime`**:
  permissionless registration → EXPERIMENTAL holds no privileges → a bare
  signer is refused `BadOrigin` → Root certifies the exact artifact hash →
  privileges on / a different bytecode stays uncertified → the trust gate's
  policy and census work through the runtime, a forbidden privilege evaluates to
  `Err(ForbiddenPrivilege(Drain))` → restriction removes the privileges.

### Negative control (the check is load-bearing)

Invert the origin check (`GuardianAuthority::try_origin`: `.is_err()` →
`.is_ok()`) and re-run:

```
test tests::the_guardian_gates_are_wired_and_refuse_an_unprivileged_caller ... FAILED
panicked at runtime/src/tests.rs:1025:
 right: Err(BadOrigin)
```

The file was restored from a byte copy and the test passes again. So the test
detects a weakened gate rather than merely exercising it.

## Not done / next

- WIRE-1 stays **open**: its second half is "at least one *non-Guardian*
  production path consults `has_guardian_privileges` before granting its own
  privileges". No such hook exists today (no pallet declares an
  `ApplicationRegistryInspect` associated type), so choosing the consumer
  subsystem (`x3-kernel`? `x3-cross-vm-router`? `x3-settlement-engine`?) is an
  owner design decision, not a mechanical wiring step. The tracker now records
  this as `WIRE-1 -> DOING` with the evidence above.
- `x3-dex` fails `cargo test -p x3-chain-runtime --no-default-features
  --features mainnet-rc1` with `cannot find macro vec` — that is a no-`std`
  *test*-build of a dependency this change does not touch (a plain
  `cargo check -p x3-dex --no-default-features` is clean). Pre-existing; not
  caused by this change.
- Pallet weights for all three Guardian pallets remain provisional
  (DB-access-weighted fallbacks), as their own `weights.rs` says.
