# X3Lang round 21 — 2026-09-18 — parallel dependency DAG (spec item 18)

Landed on `master` as `167bbe5d0` (base `01535fce7`, after another agent's merge-queue
doc PR #297). Spec build-order item 18, PHASE 16.

## The requirement, and where each clause lives

PHASE 16 asks for three things:

| Requirement | Where it is met |
|---|---|
| "Compiler must build dependency DAG" | `compiler/src/dag.rs`, built from the legs' **lowered operations** |
| "Parallelism must be deterministic" | Kahn's algorithm with a lexicographic tie-break over `BTreeSet`/`BTreeMap` |
| "Race conditions must be rejected or resolved by explicit semantics" | data dependency → edge; write-write with no dependency → refused; cycle → refused |

A leg's read/write set comes from what its operations actually do: a swap reads
its input asset and writes its output asset; a lock/mint/burn/release writes the
asset it names. Deriving it from source instead would be a second, weaker opinion
about the same question.

The artifact carries the plan rather than only the legs:
`PARALLEL_PLAN legs=3;waves=buy_eth,buy_sol|convert_eth;edges=buy_eth->convert_eth`.
"These legs are independent" is a claim about them, and a reader who cannot see
the waves cannot check it.

A `parallel` block of one leg is refused: the artifact would claim concurrent
execution of one thing.

## What the first draft of the example taught me

My first example chained three legs by accident — each consumed what the previous
produced — and the plan came out `buy_eth|convert_eth|buy_btc`: three waves of
one. The analysis was right and my fixture was wrong: there was no parallelism in
it to find. The committed example is built so two legs genuinely share a wave.

Separately, a fixture where two legs both refund the same asset trips
`no_double_refund` — correctly, because both handlers can fire. Not noise from the
new construct: the existing invariant with teeth. The example avoids it by giving
each leg its own input asset.

## One thing I initially forgot

The plan was emitted, encoded and recorded by the VM, and invisible in
`x3c explain`, because I added no disassembler arm and it printed `OP(0x55)`.
Found by reading the trace, not by a test. The trace is how a human checks this
construct, so it is the one place the omission had to be caught by eye.
