# X3Lang round 52 — 2026-09-19 — the last guard kinds, and three defects behind them

Continuation of round 51 on `master`: `95a952901` (guard kinds), `ec83c8503`
(receipt quote window), `40e8ef44b` (branch refusal), `1c665b5b1` (proof
obligation), `4d557483b` (invariant rule). Master at the end of the round:
`4d557483b`. Every change below carries the command it was measured with.

## 1. Every guard kind is decided or refused (TICKET-049 closed)

`risk`, `mainnet_safe` and `audit_gate` were the kinds a program could write that
nothing read.

| kind | decision | how it is backed |
|---|---|---|
| `risk` | decided | against `compute_risk_score`, which reads the program's own operations; a floor is refused, so is a bound that is not a number |
| `mainnet_safe` | decided | a *request* for the mainnet checks: the pass runs them when the build is for mainnet **or** the program asks |
| `audit_gate` | refused | an audit is evidence about the delivery process, not a property of the artifact — no clause can state one, no pass can read one |

The IR carries `RequireKind::RiskScore` instead of `Custom("risk_score")`, so the
pass cannot be reached by a program that writes that name as an unknown guard.
`examples/mainnet_safe_swap.x3` now states the property it is named for and passes
in dev mode. 31 tests in `compiler/tests/test_guard_declarations.rs`; the risk
tests compute the score rather than hardcoding it, and with the risk pass disabled
the three of them fail (`found: []` where an error was expected).

## 2. A receipt carries the quote window replay checks (TICKET-017 closed)

Execution refuses a stale quote before the host is asked to move value; replay
could not, because `quote_freshness` bounds an *age* and the receipt did not
carry the two blocks an age is the difference of. `TradeReceipt` now carries
`legs: Vec<LegQuoteWindow>` (venue, quote block, execution block), recorded by
the trading VM where the leg is accounted and copied in by `build_receipt` from
the state it was already handed. Replay refuses a leg priced outside the compiled
ceiling, a dropped window, and a window no leg belongs to; `format_version` is 2.
Five tests, including a forgery that is re-hashed (so the hash check has nothing
to say) and fails on the economics alone. `cargo test -p x3-lang-vm` → 59 in
`trading_execution`; the whole workspace 831.

## 3. A branch the VM cannot execute is refused, not emitted (TICKET-058, open)

Reachable from the language — `strategy X { execute { if 1 > 0 { … } } }` — and
broken at both ends:

```
before:  x3c build → 320 bytes;  x3c explain → the condition text as opcodes;
         x3c run → X3_VERIFY_FAILED: OutOfBounds(292)
after:   x3c check → "`if` cannot be executed — this VM branches on a register and
         skips four-byte instructions, and a compiler stream is framed with
         variable widths and padded …"; no artifact written
```

The emitter refused as well as the IR verifier, because `emit_x3ir` is public API
and a `check` that accepted what `build` refuses is the split this session keeps
finding. This is the fail-closed half, not the feature: TICKET-058 records what
the feature needs (an explicit jump target in the record, a reader rule, and
expression codegen into a register — the compiler emits no arithmetic at all).

## 4. The proof obligation is a mainnet requirement (TICKET-020, TICKET-024 closed)

The gate was already on `has_bridge`; the open question was warn-vs-error. Decided
by mode, which is where every other rule of this shape lives
(`verify_mainnet_safe` runs single-RPC, single-relayer, refund-path, finality and
solver-bond as errors for mainnet only). Measured first: no corpus example is
affected in either mode — every bridging example already declares both proofs —
so the promotion costs the corpus nothing.

## 5. A destination payout is not a claim of an escrow (TICKET-035 closed)

`no_refund_after_claim` warned on every check and build of
`examples/atomic_swap.x3`, the roadmap's canonical example: the rule matched
releases and refunds on `(chain, asset)` alone, so the destination *payout*
(`Release sol.SOL`) read as a claim of an escrow and the destination timeout
refund read as a double-spend of it. The rule now requires the asset to have been
locked by the program — a refund can only double-spend an escrow that exists —
with the escrow set program-wide and the ordering still atomic-scoped.

```
before:  corpus sweep → 16/23 warning-free;  x3c check --deny-warnings examples/atomic_swap.x3 → 1 warning
after:   corpus sweep → 17/23 warning-free;  x3c check --deny-warnings examples/atomic_swap.x3 → exit 0, no warnings
```

The corpus no longer produces a warning at all. The existing claim-then-refund
test now locks the escrow first — its fixture omitted the `Lock`, which is exactly
what made it indistinguishable from the payout — and a new test asserts the
two-legged shape is clean. TICKET-001 stays open for the deeper ambiguity: one
opcode meaning both a claim and a payout.
