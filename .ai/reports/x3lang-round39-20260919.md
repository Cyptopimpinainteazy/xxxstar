# X3Lang round 39 — 2026-09-19 — a slippage bound is not a risk score (TICKET-052)

Landed on `master` as `50adbcfa9` and `d40463f74` (base `9c951e8e9`; another
agent's burn-down batch 8 landed mid-round and this branch rebased onto it, then
re-ran the suite).

## The defect

`Item::RiskPolicy` lowered `max_slippage` to `RiskScore { score: max_slippage }`,
whose own range is 0..=100 — so `risk_policy { max_slippage 120 }`, a 120%
slippage bound in the order the corpus's guards are written, produced a risk score
the VM refuses and the program stopped running:

```
x3c: error: VM error: Panic("risk score: score must be <= 100")
```

Two different quantities shared one field. A slippage bound now lowers to
`Require { kind: SlippageTolerance, condition: Expression, comparison: <= }` — the
same kind and unit as `require slippage <= n`, which is also the operation the
**mainnet** slippage ceiling reads. As a `RiskScore` the policy was invisible to
that check; now a policy of 600 bps is refused in mainnet mode as 6.00%, so the
fix closes a safety hole on the way past.

Also in: `verify_risk_policy_bounds_guards` refuses a guard **looser** than the
policy it sits under — the policy says no route slips more than M, so a guard
permitting more permits what the policy forbids. Zero is "unstated" (the field is
not optional in the AST), so a program with no slippage policy cannot contradict
one. `b52_test.rs`'s `test_lowering_risk_policy_emits_score` asserted the
conflation and is re-pointed at the meaning.

## The defect it exposed

Moving a guard to the front of a bytecode stream exposed a **verifier/executor
disagreement**: `verify` advanced a fixed-frame instruction by `pc + 4` while the
executor advanced it by `align4(pc + 3)`. In a compiler stream the first
instruction is at offset 1 and the emitter pads to the next *absolute* multiple of
four, so the verifier read padding bytes as opcodes and refused an artifact the
executor runs:

```
$ x3c run a.x3b          # 176 bytes, runs fine under the executor
x3c: error: VM error: Panic("X3_VERIFY_FAILED: OutOfBounds(73)")
```

The walk reached offset 73, read a byte of a payload string as an opcode and
reported a payload length of 19535 past the end. Fixed in its own commit
(`50adbcfa9`): `pc = align4(pc + 3)`, so the verifier's boundary set is the set the
executor actually visits. For raw bytecode the two rules are the same number.

That both commits are separate matters: the verifier bug is *older* than this
round's change and a program could reach it whenever a frame was padded; the
policy change is what made it visible.

## A third finding, recorded rather than decided

`extract_slippage_bps` (the mainnet gate) reads `require slippage <= 50` as 50
**basis points**; the linter's comment says a guard literal is a **whole percent**
and multiplies by 100; `strategy.rs` compares it against `max_slippage_bps`. One
quantity, three readings — and TICKET-052's comparison is only meaningful once one
is chosen, so it is now load-bearing rather than latent. TICKET-054 records it
with the acceptance criteria (basis points is the reading two of the three already
use).
