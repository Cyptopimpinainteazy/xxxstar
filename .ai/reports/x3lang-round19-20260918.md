# X3Lang round 19 — 2026-09-18 — the opportunity graph (spec item 16)

Landed on `master` as `21cf9b2c0` (base `3328f1c83`). Spec build-order item 16,
PHASE 14.

## What landed

`venue` declarations make the language a graph: nodes are assets and venues,
each venue contributes an edge from the asset it takes in to the asset it gives
out, and the edge carries PHASE 14's whole attribute list — fee, liquidity,
slippage, latency, finality, risk, domain, proof requirement. `x3c graph` builds
the graph from a real program, searches it, and ranks what it finds, so the
module is reachable from the user-facing flow rather than only from tests.

Node kinds are one closed set with a discriminant (pool, orderbook, lending,
perp, flash, bridge, settlement) instead of a declaration shape per kind,
because the planner has to reason about them together.

## The two properties that make a graph search trustworthy

- **Deterministic**: every ordering is explicit and the ranking ends in a total
  order over the path itself. Nothing iterates a `HashMap`. A planner whose
  output depends on iteration order cannot be reviewed.
- **Bounded**: hop-bounded, and a path never revisits an asset, so a cyclic graph
  cannot produce an infinite family of opportunities.

Deliberately not modelled: price impact as a function. A venue declares a
slippage bound at its declared liquidity, and the search checks against it. A
function would be more expressive and would be a promise nothing can check.

## What this buys item 15

`require slippage <= 7` inside a `fallback` now has something to be wrong about:
when an approved venue is declared, its declared slippage is checked against the
block's bound. Before this, a venue was only a name and the bound bounded a
quantity nothing knew. Both directions are pinned in `test_venue_decls.rs`.

## The format defect this round found

`examples/atomic_choice.x3` built and then failed at run with
`InvalidOpcode(3)`; the trace showed the reader inside the middle of the
`ATOMIC_CHOICE` record.

**The invariant, now written down**: a fixed-frame instruction is *three* bytes,
and the reader advances one with `align4(pc + 3)` regardless of what the writer
emitted. A four-byte fixed frame is therefore readable only when it does *not*
start at an offset congruent to 1 mod 4. `ATOMIC_CHOICE` was
`[opcode][flags][u16]` and is the first instruction of its program — offset 1,
the one position where that breaks.

`ATOMIC_CHOICE` is now a payload op, consumed as `align4(pc + 3 + len)`, the same
expression the writer pads by, so it is correct at any offset. This also explains
round 17's observation that `x3c explain` printed garbage after the first frame:
it was this defect, not the disassembler.

The derivation says `ATOMIC_CHOICE` was the first op to violate the rule.
`REQUIRE` is also a four-byte frame and is safe only because a guard never
appears first (every intent program begins with a payload op). That is a
constraint the format enforces by accident. Recorded as TICKET-036, not silently
relied on.

## New ticket

**TICKET-036 — the first instruction of a stream must be ≤3 bytes.** A
four-byte fixed frame at offset 1 desyncs the reader, because the version byte
puts the first instruction there and the reader's stride assumes alignment. No
program hits it today (guards never lead), but the constraint is accidental and
the fix is either padding the header to four bytes or making every fixed frame
three. Needs a coordinated writer/reader change and a decision about committed
fixtures.
