# X3Lang round 9 — configuration blocks were lowered into executable instructions

Merged to `origin/master` as `5ff7c9ecf`, fast-forward from `848eff8d8`.
4 files, +115/-33.

Chasing the flagship examples' runtime panic (TICKET-025) found two fabrications
and then the real defect underneath them.

## The two fabrications, fixed

**`solver_market { mode, min_reputation }` was lowered into an executable
`SolverBid`** assembled from neighbouring fields:

```
SolverBid { solver: "competitive", receive_asset: "", deliver_asset: "",
            fee: "", bond: 95 }
```

`solver` is the *mode*, `bond` is the *reputation threshold*, and the fee and
assets are empty. A reputation threshold is not a bond. The executor rightly
refused it — `solver bid: fee must be non-empty` — so any program that
configured a solver market was unrunnable. A marketplace configuration is not a
bid; there is nothing to execute. The bond a program relies on is the guard it
writes (`require solver_bond >= N`), which `verify_solver_bond` and the risk
scorer now read instead.

**`relayers { quorum 3_of_5, relayers [...] }` was lowered into a
`RelayerAttest` with an empty signature list**, and the executor demanded
`signatures.len() >= quorum_numerator`. A compiled artifact declares its swarm;
attestations are produced by relayers at settlement, not embedded in the
program. That requirement could not be satisfied by any program that declares a
swarm, so it enforced nothing while making every such program unrunnable. The
check is now the meaningful one — a declaration cannot carry more signatures than
it has relayers — and quorum satisfaction is left to the attestation path, where
signatures actually exist. This mirrors the sibling `RpcConsensus` arm, which
validates configuration and returns.

One test had pinned the fabrication, and was corrected rather than deleted:
`test_lowering_solver_market_emits_bid` asserted that `min_reputation 1000`
becomes `SolverBid with bond 1000`. It now asserts that a marketplace
configuration does **not** become an executable bid, and a new test asserts the
bond is carried by its guard.

## The real defect underneath: guards are not evaluated

With both fabrications gone the examples got further and failed differently:

```
X3_REQUIRE_FAILED: condition register r0 is zero at pc 368
```

`Operation::Require` is emitted as `[REQUIRE][u16 0]` — no operand, no
condition, no identity. The executor's arm tests **r0**, and nothing sets r0
*for the guard*. Walking the stream shows the failing guard immediately follows
three `PROOF_REQUIRED` ops, and the mechanism is in the executor: the bulk
capability arm ends with
`vm.state.registers[0] = bytes_to_register(&result)`, while `ProofRequired`
returns `Ok(vec![])`. So an unrelated op's empty result sets r0 to zero and the
next `require` fails.

That means every guard in the language — `slippage <= 5`, `finality >= 32`,
`relayer_quorum >= 3`, `solver_bond >= 10000`, `nonce unused` — is a coin flip
on register residue rather than a check. The compile-time verifier genuinely
checks that guards are *declared*; nothing evaluates their conditions. This is
the same family as the rest of the session — a check that exists but is not on
the path that matters — and it is filed as TICKET-027 with the mechanism and the
acceptance criteria.

Fixing it is a design change, not a tweak: `Require` has to carry its condition
and enough identity to name itself, the executor has to evaluate it against the
guarded quantity, and guards whose quantity has no declaration (there is
currently no solver bond to compare `require solver_bond >= 10000` against) have
to become compile errors rather than unbacked runtime checks. I did not attempt
it at the end of a long turn; a half-implemented guard evaluator would be worse
than the honest failure.

One small diagnostic improvement shipped with it: `X3_REQUIRE_FAILED` now names
the pc. Without it a failed guard is untraceable, because the opcode carries no
identity.
