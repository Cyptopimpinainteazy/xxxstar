## How it started, and why the plan changed

`examples/arb_solana_eth.x3` fails `x3c check` with a semantic error about the guard name
`proof`. That looked like the usual staleness, so the fix looked like one word. It was
not:

```
require proof verified      -> `proof` is not a guard kind this compiler knows
require proof_complete      -> `proof_complete` without naming the proof; there is nothing
                              to have completed
require proof_complete X    -> needs `proofs required { … }` to declare X
… and then               -> `min_output 0.09` is a fractional literal
… and then               -> bridge amount must be greater than zero
```

Every step was a real requirement of the current language, and the last one was not an
example problem at all.

## TICKET-088: a route swap that states no `amount` lowered to zero

The parser's comment on a body-level swap says the amount "comes from the matching
endpoint (the same rule `bridge` follows below)". `parser::fill_route_bridge_amounts`
does fill a `Statement::Bridge` from the intent's source endpoint — but the match arm
named only `Bridge`, **and so did the function**. A swap in the same shape therefore
wrote `input_amount: 0` and was refused two passes later, by `verify_asset_moves` and
again by the IR verifier:

```
before  swap input_amount must be greater than zero
        swap has zero input_amount
after   (the amount is 500, from `from ethereum.USDC amount 500`)
```

**How that was measured.** `examples/timeout_refund_minimal.x3` is known good and its one
route step is a `bridge` with no amount. Replacing that step with a `swap` step with no
amount gives the minimal case; running the fixed and the unfixed compiler on it gives the
two lines above. Before/after, not a description of one.

The pass handles both statements now and is renamed `fill_route_step_amounts`. It was
named for the statement it happened to handle first, which is exactly why the missing
swap arm lived as long as it did: a reader looking for the rule the parser's comment
describes would not have looked here.

## The half that turned out to be a second defect

The fill can only reach a step whose `from` **is** the intent's source asset. A later
leg's input is what the previous leg returns — a market outcome rather than a constant —
so it cannot be filled, and it still lowered to `0` and produced the same "must be
greater than zero". My first version of the boundary test asserted the *refusal*, and
the test failed: lowering produced `input_amount: 0` and returned `Ok`, with the refusal
coming two passes later.

So lowering now refuses it, with the reason:

> this route step states no `amount` and the compiler cannot infer one: a step takes the
> intent's source amount only when its `from` is that source asset, and any other step's
> input is what the previous leg returns — a market outcome rather than a constant. Write
> `amount <n>` on this step.

That is the principle the comment three lines above already states for a fractional
amount ("a report about a zero, three passes after the literal that caused it"). **The
accept set is unchanged** — a zero amount was refused by `verify_asset_moves` and by the
IR verifier already — so this converts a two-passes-later refusal into a same-pass one.
No workspace test needed adjusting, which is the evidence for that claim: an accept-set
change would have moved at least one.

## TICKET-084: the stage is named, not assumed

`x3c check` reported a syntax error as `lowering failed: Parser error: expected top-level
item`. The inner message named one stage and the prefix named another, and **the prefix
is what a grep finds** — so a reader looking for the defect was sent to the wrong pass.

```
before  x3c: lowering failed: Parser error: expected top-level item
after   x3c: parsing failed: Parser error: expected top-level item
```

`X3Error` gains `stage()` and `staged()` — one mapping, next to `span()`, exhaustive over
the twelve variants so a new variant cannot be added without a stage — and both call
sites that hard-coded the prefix ask the error instead.
`check_names_the_failing_stage_rather_than_assuming_one` pins both directions, including
the negative: a syntax error must **not** contain `lowering failed`.

## Found while doing it: TICKET-089

Trying to write the probe files kept hitting a parse error in *my* fixtures, which turned
out not to be mine. From the known-good `timeout_refund_minimal.x3` with one guard
inserted before its `timeout`:

```
require slippage <= 50      OK
require slippage <= 0.5%    OK
require slippage <= 1%      FAIL  unexpected clause in intent body: Ident("45s")
require slippage <= 2%      FAIL  unexpected clause in intent body: Ident("45s")
require delta <= 0.01%      OK    (parses; then a semantic error, unrelated)
```

The split is **whole versus fractional**, and the parser's own comment at
`parse_whole_percent_bps` says why: "`70%` is an integer followed by `%`, while `0.5%` is
a single percentage literal whose text still carries the sign". The fractional form is one
token and is handled; the whole form is `Int` then `Tok::Percent`, and a `require` guard's
value goes through the general expression parser — so `1 %` is read as a binary **modulo**
that keeps looking for a right-hand operand, and the next clause is consumed as that
operand.

That is why it survived: a percent guard written as the last clause of a body works, which
is where the passing examples and test fixtures happen to put theirs. `1%` is the most
natural way to write one percent, and the refusal names the **next** clause — a correct
line — rather than the guard.

The error path is not the whole risk. `require slippage <= 1 % 50` would parse as a
modulo and mean something no author intended, silently. TICKET-089 records it with the
reproduction, the identified cause, and the acceptance criteria: make the whole form parse
as the fractional form does, at the guard's value path — not by removing `%` from the
operator table, because a modulo is still a modulo.

## What TICKET-083 still needs, corrected

`examples/arb_solana_eth.x3` is **not** stale syntax. It is a current-dialect program that
needs: the guard renamed to `proof_complete` plus a proof named, a `proofs required { … }`
block declaring it, and base units for `min_output` (`min_output` carries no asset, so a
fractional literal is refused rather than converted against decimals the compiler cannot
see — 0.09 SOL at nine decimals is `90_000_000`). When those are written, the route's
second and third steps also need explicit amounts, because they follow the first leg and
the fill cannot reach them (TICKET-088's boundary). Five of the six files TICKET-083
names are genuinely in the dead `contract … { fn … }` dialect; this one is a documentation
bug that reads as a syntax bug.
