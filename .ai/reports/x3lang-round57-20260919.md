## The cause, and why it is a consensus problem

`Operation::Emit { data: HashMap<String, String> }`, and `emitter.rs:310` writes it with
`format!("{}:{:?}", name, data)`. `Debug` for a `HashMap` prints in **iteration order**,
and `RandomState` is seeded **per map instance** — the thread-local is initialised once
from the system and then bumped on every `RandomState::new()`. So two maps built from the
same entries in the same process iterate differently, and that order is the artifact.

`Operation::RouteScore { weights: HashMap<String, u32> }` had the same shape via
`weights.iter().collect()` into the payload vector, and `verify_route_score` iterates the
same map to name every overweight key — so the *diagnostic* could differ too.

Why it matters beyond tidiness: the artifact's bytes are what PHASE 45's version binding,
the `--provenance` document and the bytecode hash all refer to. A build that is not
reproducible makes "which source produced this artifact?" unanswerable by hash, and the
bytecode is consensus-relevant input.

## The fix, and the after-measurement

Both fields are `BTreeMap`. The rendered shape is unchanged — `{:?}` on a sorted map is
the same `{"k": "v", …}` — so nothing but the order moves, and the order now comes from
the program:

```
$ for i in $(seq 1 24); do x3c build probe_emit.x3 --out pe2/$i.x3b; done
$ sha256sum pe2/*.x3b | awk '{print $1}' | sort -u | wc -l
1
$ x3c explain pe2/1.x3b | grep -i emit
  0003  0x60  EMIT  trade_seen:{"arg0": "…", "arg1": "…", "arg2": "…"}
```

## The test that should have caught it, and did not

`compiler/tests/property_tests.rs` has contained this since it was written:

```rust
let mut weights = HashMap::new();
weights.insert(strategy.clone(), score);          // one entry
ir.push(Operation::RouteScore { strategy, weights });
let bc1 = emit_x3ir(&ir)?; let bc2 = emit_x3ir(&ir)?;
assert_eq!(bc1, bc2, "IR emission must be deterministic");
```

**One weight.** A one-entry map has no order to disagree about, so the assertion was true
and said nothing. It now generates three weights, two of which are the point of the test.
This is the same failure mode as the `verify_valid_receipt` that asserted success against
`block_hash = [0xab; 32]` (TICKET-065) and the `keccak256` test that asserted "not all
zeros": **a test whose input cannot express the property it names**.

The reproduction is kept at the language level as
`an_emits_payload_map_does_not_reach_the_artifacts_byte_order` — a strategy module with
`emit trade_seen(1, 2, 3)`, sixteen compiles compared, and a first assertion that the
payload really is in the artifact so the byte-identity is about this map rather than
about the compiler ignoring it.

## What this round did **not** build, stated plainly

No gate fails when a *new* file gains a `HashMap`. The classification is this report
rather than a test, deliberately:

- a file-level allowlist would not catch a new **ordering-sensitive use** inside a file
  that is already listed — which is exactly how this defect survived;
- a per-site regex gate over Rust source has the false-positive problem that
  `contains("rand::")` demonstrated last round (it matches `Operand::Reg`).

What does bite is the pair of byte-identity tests, which fail on any non-determinism
however it is introduced — including one no type scan could see, like a clock reached
through a dependency. That is a stronger gate than a type scan, and it is where a future
gate should be written.
