# X3Lang round 48 — 2026-09-19 — `x3c fmt` keeps the comments (TICKET-043)

Landed on `master` as `248b59c91` (base `b6a9a231d`). Closes TICKET-043.

## The loss

The lexer treated a comment as whitespace. That is what made the parser work, and it
is why `x3c fmt` deleted every comment in whatever file it was pointed at. For this
repository that is documentation loss rather than cosmetics: the examples' comments
are the reasoning the phase audits cite, and round 33 could only make the loss
*visible* — count the comments, warn — because nothing the formatter walked held one.

## The lexer keeps them

`TokenKind::Comment(CommentKind)` carrying the comment's span. `Line` and `Block` are
distinguished because a formatter writes them differently, and because an
unterminated block comment is the one the lexer reports rather than swallowing (that
behaviour is unchanged and still fail-closed).

The parser steps over them: `lexer_token_to_tok` returns `None` for a comment, so
the grammar sees exactly what it saw before. `parser::source_comments` reads the same
stream and slices the text by span — which **replaces** the source-text scanner I
wrote for round 33's warning. One reader for "what a comment is", not two.

## The formatter puts them back

`format_program_with_comments` writes each comment before the top-level declaration it
precedes. The AST holds no comments, so that is the finest association available
without re-parsing — a comment written *inside* a declaration moves to that
declaration's boundary. Moving beats deleting, and the CLI says which trade it made:

```
$ x3c fmt examples/objective_routing.x3
x3c: warning: 49 comment(s) were placed at declaration boundaries: the formatter has
nowhere else to put one, so a comment written inside a declaration moves to the line
above it
```

and the file still checks (`6 ops, no semantic errors`), with its header block intact
where it was.

## Evidence

```
cargo test --workspace --no-fail-fast -> 71 suites, 794 passed, 0 failed
cargo clippy --workspace --all-targets -- -D warnings -> exit 0
cargo fmt --all -- --check -> exit 0
python -m pytest -> 14 passed
x3c fmt on a 49-comment example -> comments kept, file checks
corpus sweep -> 17/23 check, 17/23 build, 16/23 warning-free, 17/23 run
                (origin/master control: 16/22, 16/22, 15/22, 16/22)
```

`formatting_keeps_the_comments_it_can_place` asserts the header (including a bare `//`
line — the lexer counts it, my first expectation did not), a trailing note, the
header's position above its declaration, that the formatted text compiles to the same
bytecode, and that formatting again changes nothing. The lexer's own
`line_comment_at_start_of_file_is_skipped` is renamed to
`…_is_a_comment`, because "skipped" is no longer what happens.

## What is *not* claimed

A comment's **line** inside a declaration is not preserved — it is placed at the
declaration's boundary. Preserving the line needs comments attached to AST nodes
rather than to the item they precede, which is a larger change (every node that can
hold one, and the formatter's emission points). The ticket says so rather than
implying the formatter is now exact.
