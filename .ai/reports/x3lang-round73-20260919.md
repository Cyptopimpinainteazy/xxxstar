## 1. `0ddbb26ad` — PHASE 48 row 24, `dropped transaction`

Row 24 sat **unverified** since the matrix was built, because a keyword count could not tell
coverage from noise. Reading it found the case depends on a contract that no file stated.

A dropped transaction is a venue that **answers**: it accepted the transaction and broadcast
it, and it reports the state it started from, because nothing moved. Whether that is
distinguishable from a settled leg is decided by `TradingVm::check_commitment`, which
requires every venue result to equal `CapabilityManifest::state_commitment`. Measured, all
four combinations:

```
anchor=PRE  | venue landed (reports POST) -> Err(StateCommitmentMismatch)
anchor=PRE  | tx DROPPED (reports PRE)    -> COMMITTED, receipt emitted
anchor=POST | venue landed (reports POST) -> COMMITTED
anchor=POST | tx DROPPED (reports PRE)    -> Err(StateCommitmentMismatch)
```

**The first reading had it backwards, and that is worth recording.** The initial reproduction
anchored the manifest at the pre-state, which made the *landed* venue look like the defect and
the dropped one look innocent. The 2×2 is what settled it. `CapabilityManifest::state_commitment`
carried no doc comment, so nothing said which of the two anchors it is — the field now says,
with the inversion stated as the reason the doc exists.

`a_dropped_transaction_is_not_a_settled_leg` asserts the refusal **and the control in the same
test**, because a test asserting only the refusal would pass against a runtime that refused
every leg. It pins the refusal as `StateCommitmentMismatch` rather than any error, and that the
dropped leg leaves `receipt_emitted = false`, `committed = false` and the journal untouched.
Load-bearing, verified by mutation: with `check_commitment` neutered to `Ok(())` it fails
(`a leg that reports the state it started from did not settle`) and passes with the check
restored. The `Host` fixture gained a `reported_commitment` field defaulting to `COMMITMENT`,
so no existing test changed behaviour (13 tests before, 14 after).

The row's scope limit: `x3c receipt execute` derives the field from the compiled bytecode and
runs `CapabilityMode::Fixture` under `ExecutionMode::Development`, and a fixture manifest is
refused in production mode (`TradingExecError::NonProductionCapability`) — so that surface is
an artifact binding, not evidence for this row.

PHASE 48's 30 named cases are now all covered. The phase's sentence is "every economic feature
must include hostile tests" and 30 cases is a sample of that, not a definition of it, so the
claim is **complete against its own list**.

## 2. `1f976974a` — TICKET-075 / PHASE 39: the guarantee reaches the artifact

The clause was enforced at compile time and then dropped: a venue lowered to no operation, so
the emitted bytecode said nothing about whether a leg is atomic, escrowed, pre-funded,
attested or merely compensated. A counterparty, an auditor or a replayer holding only the
`.x3b` could not see the assumption the trade rests on — half of what the phase asks for, and
the half that does not need the source.

The mechanism is the one TICKET-059 established for finality depth: the declaration lowers to
an operation that carries its values. `Operation::VenueSettlement { venue, guarantee }` is
emitted as an inline record at a new opcode `0x58`, in the `0x5x` declaration block beside
`STRATEGY_LICENSE`, in the `[opcode][u16 len][payload]` shape `ROUTE_FALLBACK` uses and
registered in the one `is_payload_opcode` table both the disassembler and the verifier walk by:

```
$ x3c inspect artifact.x3b
  0009  0x58  VENUE_SETTLEMENT   venue cex_hedge settles compensating
  0010  0x58  VENUE_SETTLEMENT   venue pool_plain settles none
```

`guarantee` is an `Option` and the absent case is a present-but-empty shape field, not a
missing separator, so a truncated record is refused rather than read as "states none". That
matters because the compiler *requires* a guarantee of an `orderbook` venue and leaves an
on-chain venue that states none alone — two different facts about a trade, and one test asserts
the absence rather than only that something arrived.

### Two self-corrections, both found by tests rather than by reading

- **The executor's validation was unreachable.** The first version of the test expected the
  executor's own refusal code and got `X3_VERIFY_FAILED: InvalidOperand(180)`. `VM::execute` is
  `verify_and_execute`, whose only callee of `execute_unverified` it is, so no public path
  reaches the executor without the verifier. The rule belongs in `verifier::verify` — one
  reachable enforcement point — and the executor arm now only advances the pc past a record the
  VM does not act on. A second copy would have been a rule nothing exercises.
- **The verifier and the compiler disagreed about a blank name.** `verify` used
  `venue.is_empty()` where the compiler's checks use `trim().is_empty()`, so an all-spaces
  venue name passed the VM and was refused by the compiler. Found by the test for it, aligned,
  and the reason is in the comment.

### What the change surfaced: TICKET-097

Adding an opcode inside `BYTECODE_VERSION_1` is invisible to the version byte. Every record
added this session and before — `0x54`…`0x58` and the whole `0x80..=0xAB` block — travelled
inside the same version, and `is_payload_opcode` is the single boundary source for both the
disassembler and the verifier. A reader that predates an opcode therefore **misparses** it
rather than refusing it, which is worse than a refusal because a refusal is visible. Nothing
exchanges artifacts across runtime versions today (`x3-lang`'s artifact has no consumer outside
its own workspace — verified, the only other mentions are comments pointing at the real
crates), so the risk is latent; it stops being latent the first time a `.x3b` outlives the
runtime that produced it. Recorded as TICKET-097 with the gate it asks for rather than changed
here, because bumping the version is a coordinated change with its own blast radius.
